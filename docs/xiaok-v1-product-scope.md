# 家客来 1.0 产品范围（I7.2）

> 依据：《家客来_小K_功能清单与四端UI基线_V3.docx》（V3.2，2026-10-10）与 2026-11-14 用户路线调整。
> I7.2 把 I7.1 的代码能力接入真实隔离数据库、Worker、小程序和四端业务，完成第一版真实运行验收。真实微信订阅消息、生产部署和真实小程序点击仍未执行。
> 本文只定义第一版交付边界，不删除既有防水、水电专业 Agent 的代码、发布版本和历史验收记录。

## 1. 第一版目标

家客来 1.0 = **十阶段轻量 Agent + 主动装修提醒 + 阶段知识问答 + 四端角色化周报**。

第一版优先让业主、设计师、公司老板、施工人员每天真正用起来，而不是先完成高阶专业工作流：

- 小K 是持续服务的装修助手，不是“管理 SaaS + 聊天框”（R-01）。
- 按用户、项目、阶段、权限和偏好提供当前相关服务（R-02）。
- 四类角色共享同一项目事实（R-04）。
- 业主端以连续对话为主（R-05）；设计师、老板、施工人员使用各自工作入口（R-06）。
- AI 尽量代替重复记录劳动（R-08），普通记录不默认逐条人工审核（R-09）。
- 进度使用提前绿色、正常黄色、落后红色，无法核实为灰色（R-10）。
- 保留问题与已修正清单（R-11），支持跨天持续委托（R-12），模块化复用（R-13）。

装修阶段保持十个，不增不减：

| 顺序 | 阶段 ID | 名称 | 现有 Construction 阶段键 |
| --- | --- | --- | --- |
| 1 | `pre_construction` | 前期 | `preparation` |
| 2 | `design` | 设计 | `design` |
| 3 | `demolition` | 拆改 | `demolition` |
| 4 | `utilities` | 水电 | `utilities` |
| 5 | `masonry` | 泥木 | `masonry_carpentry` |
| 6 | `painting` | 油漆 | `painting` |
| 7 | `installation` | 安装 | `installation` |
| 8 | `furnishing` | 软装 | `furnishing` |
| 9 | `completion` | 完工 | `completion` |
| 10 | `occupancy` | 入住 | `move_in` |

阶段 ID 用于 Agent、知识包、提醒策略和周报模板；现有 Construction 阶段键继续作为业务事实键，避免迁移历史项目和破坏既有权限。

## 2. 第一版必须交付

### 2.1 十阶段轻量 Agent

- 统一的 Stage Agent 注册表，十个阶段均登记 `agentId`、`stageId`、名称、描述、支持意图、知识包、提醒策略、周报模板、工具权限、版本和状态。
- 统一接口：阶段识别、阶段知识问答、阶段主动提醒、阶段进度读取、阶段待办整理、阶段周报生成。
- 十套阶段配置共享同一模型网关、会话上下文、项目/房间权限、Construction 事实、通知回执、持久任务、Evidence 和 Token 台账。
- 不为每个阶段复制运行时；阶段 Agent 不直接写正式业务数据库，所有正式操作走现有业务服务。

### 2.2 阶段知识问答

- 每个阶段至少一组基础知识包：阶段介绍、常见问题、业主关注、施工人员关注、常见资料缺项、下一阶段衔接、回答边界、可引用企业/公开资料。
- 优先复用 KnowledgeRetriever、企业知识库和已核验公开来源。
- 企业资料未配置时，明确说明“本次未核实企业施工标准”；允许标注通用装修知识，不得伪装成企业规定。
- 禁止编造施工尺寸、材料参数、验收数值、闭水时长、电线线径、水管管径和施工完成事实。

### 2.3 主动装修提醒

- 统一 Stage Reminder Engine，触发来源：阶段变化、有效计划节点、节点到期前、责任人待办、业主待确认、设计师待核对、施工人员待补资料、资料长期未更新、问题超期、阶段即将结束。
- 每条提醒具备 `reminderId`、企业、项目、阶段、目标角色、目标用户、关联任务/问题、触发类型、触发依据、计划时间、发送时间、状态、去重键和动作入口。
- 支持去重、暂停、取消、阶段变更重评、权限撤销停止、发送失败保留失败状态并可重试。
- 第一版优先站内提醒和待办；微信订阅消息只在已配置、已授权且回执可验证时标记已发送。
- 提醒文案由服务端事实和受控模板生成，模型只负责自然语言表达；模型失败不丢失原始事件。

### 2.4 四端角色化周报

- 统一 Weekly Report Engine，数据来自 Construction 项目事实、有效计划、已发布施工记录、当前阶段、待办、问题、整改、复核、业主确认和真实回执。
- 四类报告：业主周报、设计师周报、公司老板周报、施工人员周报；老板支持跨项目汇总。
- 每份报告绑定报告 ID、类型、企业、项目、接收人、角色、周期、来源快照版本、来源引用、生成时间、报告版本和投递状态。
- 同一周期、同一接收人、同一报告类型幂等；生成失败可重试；发送失败不能伪装成功；数据修订保留原版本和生成时快照。
- 第一版优先站内周报，复用现有 `construction_reports` 的周期、事实、版本和投递管线。

### 2.5 进度红黄绿

- 计划状态：提前（绿）、正常（黄）、落后（红）、待核实/未排期（灰）。
- 施工状态：未开始、施工中、待验收、已完成，与计划颜色分开显示。
- 问题状态：待核实、待整改、整改中、已整改待复核、已修正、已排除。
- 计划状态来自有效计划版本，实际完成来自真实施工记录；没有计划和实际记录时显示待核实。
- 不生成没有工作量口径的精确完成百分比；多房间并行分别统计；四端使用同一计算服务。

### 2.6 四端界面

- 业主端：默认与小K连续对话；增加当前阶段提醒、本周项目周报、当前待办、阶段知识问答、历史周报。
- 设计师端：默认当前设计任务与待核对事项；增加本周工作摘要、待处理需求、设计提醒、历史周报。
- 老板端：默认公司项目主动简报；增加跨项目周报、红黄绿、需要介入的例外、问题与已修正清单、历史周报。
- 施工端：默认拍照、语音、当前任务；增加本周施工任务、阶段提醒、待补资料、本周施工记录摘要、施工周报。
- 四端共享同一业务事实，不把四端做成同一个聊天首页，移动端沿用现有规范。

### 2.7 十阶段配置初始化

十阶段均交付阶段简介、常见问答、关键关注、进入阶段提醒、阶段中期规则、结束准备提醒、下一阶段衔接和周报内容配置。提醒优先由真实阶段变化、有效计划和待办触发，不固定骚扰。

## 3. 第一版不做

以下能力不阻塞 I7.1 交付：

1. CAD 自动解析和修改。
2. 图片图纸 OCR。
3. 精确现场测量。
4. 自动工程质量认证。
5. 自动验收和放行。
6. 全部国家规范现行性研究。
7. 完整托管 RAG 企业知识管理。
8. 多专业 Agent 复杂协同。
9. 摄像头实时监控。
10. 完整采购、库存、结算。
11. 复杂报价系统。
12. 所有施工节点的自动化专业审批。

## 4. 后续增强

- 图纸与 CAD 解析、OCR、照片质量与量测辅助。
- 专业验收、整改复核、放行与处罚流程。
- 企业知识托管、规范现行性目录和更强的来源治理。
- 微信订阅消息、短信、电话等外部触达的规模化运营。
- 多项目组合分析、成本/工期预测和供应链协同。

| 能力 | 复用方式 |
| --- | --- |
| Specialist Registry / Router | 保留 `waterproof-specialist`、`electrical-specialist` 及其发布版本；阶段问答遇到深入专业问题时可转交。 |
| AgentModelGateway | 阶段问答与提醒文案需要模型时复用同一网关、加密配置、Responses/Chat Completions 路由和用量台账。 |
| KnowledgeRetriever / Evidence | 企业知识、公开来源、引用校验和原件读回继续走现有服务。 |

| 四端现有页面 | 复用 assistant followup、owner-daily、boss-weekly、stage-reminder、construction projects/brief/chat 等页面和组件。 |

## 6. 验收标准

第一版完成必须满足：

1. 十个阶段均有统一轻量 Agent 注册和配置。
2. 十阶段基础知识问答可运行，且有来源/边界声明。
3. 小K 能根据项目真实阶段主动提醒。
4. 提醒可去重、暂停、取消、恢复和失败重试。
5. 四端拥有各自角色化周报。
6. 四端周报读取同一 Construction 事实。
7. 周报可追溯来源和生成时版本。
8. 红黄绿状态统一且有真实依据。
9. 施工人员普通记录尽可能免填表。
10. 防水和水电专业 Agent 作为高阶能力保留。
11. 十阶段配置可持续扩展，不复制运行时。
12. AI 不可用时原始业务和人工操作不受影响。

验收结果分别标记 `passed`、`failed`、`limited`、`not_run`、`unknown`。高阶专业能力未完成不得阻塞第一版交付。

## 7. I7.2 真实运行边界

- 提醒在隔离 PostgreSQL 17 中由真实 Worker tick 生成，覆盖十个阶段、计划临近/过期、角色待办、记录停滞、暂停/恢复/取消、撤权、失败重试、安静时段和站内回执。
- 老板只接收真实计划或约定期限例外；普通待办留在责任角色。老板跨项目提醒同一主题 24 小时内去重。
- 四端周报复用 `construction_reports` 事实、版本和投递管线；同一周期幂等，修订生成新版本，历史版本保留。
- 业主 C01 在原会话内使用当前阶段知识回答；深入专业问题继续转交防水/水电专业 Agent。企业 KnowledgeRetriever 尚未注入，回答明确声明未核实企业标准。
- 提醒和周报事实不依赖模型。模型只负责周报正文自然语言整理；未配置模型时保留 `facts_only`，不伪造统计。
- 没有真实约定期限的事项不生成超期提醒；没有有效计划不生成精确到期提醒；没有真实记录不判定停滞。
- 真实微信订阅消息未配置时只标记站内 `delivered`，不伪装为已发送。

完整矩阵见 [I7.2 真实运行验收](./xiaok-i72-live-acceptance.md) 和 [发布就绪度](./xiaok-v1-release-readiness.md)。
