# 小K对话整体规划

**当前有效计划｜2026-10-19整理。** 本文件统一维护产品目标、能力差距、后续顺序和验收要求；阶段编号沿用既有能力标识，已交付基础直接复用。历史方案、迁移、模型/prompt版本、执行次数和逐批测试记录引用第2节文档，不再在本文件追加“本轮/当前批次”日志。

本文件维护开发方向和验收范围，不以计划替代实现证明。实现事实以当前代码、测试及模块清单为准；设计来源以PPT及路由唯一最新批准稿为准；生产发布另行授权。

## 1. 产品目标与统一约束

### 1.1 第一主线：专业智能客服

小K首先要能回答装修专业问题：理解用户在问什么，按需查企业知识和本人有权查看的工地事实，给出有依据的解释、比较和建议，并承接连续追问。资料关联、节点补问和持续事项服务于这条主线。普通答疑可直接完成；需要实际核对/处理时再接续团队。

例如“现在加洗碗机会不会影响安排”，应结合企业专业做法、本人实际施工阶段、已知设备需求及有效图纸，说明已知条件、可能影响与仍需核实之处。项目事实未查到时明确未知，不能只复述节点、只列检索原文或直接宣布工期变化。

| 信息来源 | 在回答中的职责 | 事实边界 |
| --- | --- | --- |
| 企业知识库 | 提供已发布、适用的工艺、材料、服务和规则依据 | 保留出处、页段/表格、单位/例外、受众、有效版本和适用条件；上传时间不代表生效优先级 |
| 大模型 | 理解意图/指代、组织多源证据、解释原理与取舍、自然追问 | 一般建议与企业规定分开；不生成现场事实、企业承诺或正式批准 |
| 实际工地 | 提供正确项目/房间的实际节点、需求、记录、图纸、事项和处理结果 | 按角色实时查询，携带业务版本、记录/查询时间及缺项；计划、实际、完成、验收分开 |
| 当前会话与记忆 | 延续已明确对象、原话、偏好、更正及未解决问题 | 记忆不能替代正式业务事实，不跨房屋/客户混用，不覆盖独立需求 |

保留一期保守摘录模式，生成式解释按本计划单独验收。动态工地事实不复制进通用知识库作为第二份事实源。专业解释须让企业依据与项目事实进入同轮回答；检索/工具成功、固定displayText或摘录列表不能单独代表综合问答完成。

### 1.2 客户体验与团队分工

- **聊天优先**：用户可以先问问题、预算未定、换题或更正。五类需求是内部理解结构；不强迫答完问卷、看进度、保存/确认摘要、收藏参考或填写资料包。短回顾可选，旧已确认记录与历史入口继续兼容。
- **图片直发**：不先分类、选房间/户型版本；上下文唯一时服务自动关联，缺项/歧义才最小澄清。员工核对分类和资料归属，客户无需重复上传。上传参考图不写正式v4墙图；正式墙图通过只读适配器消费。
- **人工接续**：明确找真人即在原聊天提交，不增加资料分享授权卡、摘要/建档或手机号前置。另行电话联系单独同意；拒绝电话仍可站内接续。复杂判断、正式报价/具体工期等交接待设计师协调，一般专业解释仍可由小K回答。
- **模式一致**：等待可补充资料，暂停自由AI回复和主动需求追问；仅显示真实状态/确定性反馈。客户可取消回AI；真人接管后无迟到AI，员工退出回等待、明确结束再恢复AI；不可用不虚构在线或回复时限。
- **联系规则**：普通沟通时间在聊天商量，不建立沟通预约/确认时间流程。PPT18/21“联系管家”拨打当前阶段获权员工的实时电话，到场/改期/取消由电话协调；不写施工到场意向，不改正式量房预约。
- **角色分工**：设计师核对资料、专业回复及方案差异；经理建立/安排工地成员、实际阶段和处理事项；施工人员同聊发图文、核对发布；老板/运营按权限审核、协调及提供设备售后。减少各角色重复录入，客户不管理内部任务、版本、技术配置或退款对账。
- **共享范围**：每个企业/工地一份经理、工人、获派设计师共享小K对话，成员看到同一原话、附件、草稿和版本；修改/发布仍受作者、经理及版本约束。不同工地、业主私人咨询分别隔离，业主只读明确发布/授权投影。
- **少打扰跟进**：节点仅补必要缺项，已知/已问/已推迟内容不反复追问，可随时换题。照片关注与正式问题处理分开，“有进展告诉我/不用提醒”支持真实订阅及取消，微信订阅按场景另申请。

### 1.3 事实、权限与可靠性

1. 原话、模型观察/推断、客户明确表达、员工核实、正式批准、已发布记录分别溯源。更正保留supersedes链，只影响对应对象/字段；员工核实或模型置信度不等于客户批准。
2. 每项资料关联保留资源ID/版本或hash、项目/房间映射、原始message/media、受众、关联依据、查询时间与有效状态。明确有效版本/发布关系优先于相似度或上传时间；同名/相似度不等于已关联；明确关系可自动验证，歧义/冲突才核实。缺图、过时或版本冲突仍回答有据部分并说明最小缺项。
3. 一般讨论、假设、图片观察不自动建正式事项。实际处理沿同一issueId/revision保存负责人、等待对象、状态、依据和回传；回复、发布、客户决定、落实、解决、关闭各有业务条件。缺负责人如实待分配，回复不自动解决，关闭不代表工程验收/付款。
4. 联系、具体公开范围、正式方案及费用/工期、订单/付款/退款决定只在必要时明确确认，绑定精确对象与版本；普通“好”、沉默、浏览不算批准，新版本不继承旧同意。拒绝/暂后不锁住聊天，提交/批准/落实/到账分别据真实回执说明。
5. 企业、参与者和资源授权由服务端及共享租户机制决定，覆盖检索、媒体、缓存、历史、派生记忆、工具、任务和投递。成员移出/停用、来源撤回/换版须使相关访问与派生结论失效；资料中的文字/指令不能改变系统授权。管理权限沿isEnterpriseManagementRole，平台管理者在明确企业内继承企业管理能力，不强制成为项目员工。
6. 会话可先于线索/项目存在，受控关联后延续原会话；不以leadId/projectId等替代会话身份。接待权限不等于企业全部私聊或项目资料权；线索来源、作品作者、接待人、负责人、分佣依据保持分离。
7. 沿用现有run/job/step/outbox、Worker租约、短事务、来源/业务版本、幂等和用量。模型/存储网络调用置于事务外；有界循环有轮数/超时/预算，未知写入按原operationId核对，恢复/重投不重复副作用；checkpoint不保证外部exactly-once。
8. 同轮图文绑定明确turn，媒体由服务端解析获权引用，只向该租户允许的provider发送必要资料，不抓取模型/客户端任意URL。消息采用版本化内容块与文字回退，不执行模型HTML或任意路由。回复提交前重验源、revision及人工模式；无视觉能力明确降级，单图不确立承重/精确尺寸/隐蔽质量。按模型实际image/tool/structuredOutput/streaming/usage/context能力接入，发送必要资料，日志不默认复制原图/录音/完整对话。
9. 记录provider/model、prompt/policy、输入引用、耗时、错误和用量；图片计入预算，未知费用为未知。上下文按预算选相关双方消息、事实、更正、事项与证据，不每轮重发全部历史；保留期覆盖摘要、观察、checkpoint及调试副本。语音原音/转写/纠错复用同一核心，图像生成仍属既有AI工作台。
10. 持续事项区分待核对/补充、待团队、待客户决定、待执行、已解决/关闭及暂停/取消，状态转移须有真实依据；未约定时间不记逾期。实际节点、资料/版本、成员/模式及处理结果事件通过受控消息入口驱动续办/投递，不伪造用户提问、不依赖页面在线；关注取消、改期和撤权阻止旧任务复活，投递/发送失败可恢复但不自动扩大受众。

### 1.4 技术路线与开源借鉴

复用当前LangGraph JS及现有业务适配器，知识检索、模型解释、受控工具和确定性业务步骤协同；框架不替代数据库的任务、权限、来源和业务事实权威。增量接入并保持会话/历史兼容、企业开关与可回滚路径；核心通过注册契约接业务，由应用装配跨模块依赖，不维护第二套任务/权限/事实系统。

上下文/记忆、任务状态、对象版本、规则/工具、恢复/人工接续、权限、质量和模型成本的已有基础、待补方案及开源采用边界统一维护在[Agent工程专项](./xiaok-agent-engineering-plan.zh-CN.md)。知识入库/检索细节仍归[企业知识库专项](./xiaok-enterprise-knowledge-plan.zh-CN.md)，此处不重复展开。

扩展前复核维护中源码、测试和供应商问题，核对固定版本、许可、数据边界和成本；配置模型通过本期场景后再采用。框架迁移/重写须有具体收益，不因专项规划引入第二套执行系统或升级实现状态。

## 3. 后续开发顺序与业务接入

### 3.1 唯一主线顺序

当前由本对话统一负责两个专项、共享接口、集成和验收；以下按领域分工，不要求两个聊天并行或两边平均改动。用户已授权按实际依赖连续实施完整业务批次，完成实现、必要客户端、自动化和双语文档后报告并继续，不逐批等待确认。设计和生产部署仍守原边界。

工程开发按领域分开：小K客服/Agent专项拥有对话、记忆、工具/项目上下文、模型与最终回复；知识专项拥有资料、索引、检索、知识版本/定位和运营。双方沿既有KnowledgeRetriever/Evidence与来源重验对接，源码、测试及故障分别归属；接口变化由明确负责人接入受影响的联合回归。保留同一产品主线和权限/任务基础，遗留混合适配按触达渐进提取，不把知识库工作再次扩展成Agent重构。唯一边界见[二期合同](./xiaok-assistant-phase-2.zh-CN.md#agent与知识库的开发边界)。

按“专业问题能答好 → 结合实况能解释 → 需要处理能跟到底 → 正式处理及经营服务贯通”推进。现有P5等基础不因排列在后面而重做；若已有批次仍在授权验收中，按其既有合同收口，新增工作优先补专业问答。每批同时接小程序和真实服务，不另设最后统一客户端集成期。

### 4.3 PPT视觉基准与每次还原后的自动化验收

<a id="36-既有计划与ui回查修正"></a>

**每次涉及小程序界面还原、关键变体或可见状态调整，开发后都必须自动化测试还原程度，功能与视觉分别验收。** 采用2.2所列PPT、台账中的路由唯一最新批准稿及已还原界面。原PPT单屏853×1844按宽映射390×844；批准独立稿有不同原始画布时按其实际比例映射，不拉伸。拼板仅总览；S04以原PPT22/38为主稿，未采纳过程稿不覆盖。

缺稿重新生成时，先从对应/相邻PPT提取画布、布局层级、绿白配色与柔和背景、字重/换行、气泡/卡片比例、图标及小K插画语言，记录参考页与组件映射；只保留绿色/小K不算延续设计感。新稿明确批准后才实施并替换唯一设计源；普通状态复用批准组件/状态说明，无需逐张补图批准。业务插画按项目规则独立生成透明PNG，入包≤300KB，不用WebP，不切片/裁剪整屏设计充当产品UI。

| --- | --- |
