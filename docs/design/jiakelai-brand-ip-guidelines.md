# 家客来品牌 IP 与产品界面融合规范

> 状态：已确认的品牌设计方向
>
> 更新日期：2026-07-30
>
> 适用范围：家客来微信小程序、运营物料及后续品牌化产品界面
>
> 实施说明：本文记录设计决策，不代表相关页面已经完成开发。生产功能、数据和权限始终以当前代码及模块清单为准。

## 1. 设计结论

家客来采用以下品牌形象组合：

**F1 角色本体 + F3 空间变形机制 + F2 辅助几何语言**

- F1 负责角色记忆、亲和力和稳定识别。
- F3 负责表达量房、户型、空间生成和方案交付等产品能力。
- F2 不作为主角色，用于沉淀 JK 曲线、门框、房屋轮廓和空间路径等辅助图形语言。

核心角色名称为 **“小K”**。名称变更只影响角色的文字称呼；已确认的 F1 角色本体、F3 空间变形机制和页面应用方向保持不变。

小K不是页面装饰或一次性吉祥物，而是“懂空间、能行动、陪用户完成家居服务流程”的品牌伙伴。后续页面默认沿用已经确认的 **C 版“客户档案簿”方向**：通过一个与当前业务有关的实体隐喻，把 IP、信息结构和交互控件融合为同一套页面语言。

## 2. 名称、Logo 与 IP 的关系

品牌识别链必须保持连续：

| 品牌资产 | 主要职责 | 设计要求 |
| --- | --- | --- |
| 家客来名称 | 被记住 | 保持“为家庭服务的人”的人格感和陪伴感，并强化服务来到家中的行动感 |
| Logo | 被识别 | 保留房屋轮廓、JK 字母结构和明亮绿色；该 Logo 已按“家客来”完成设计 |
| 小K IP | 被喜欢、被理解 | 通过表情、动作、工具和空间变形进入真实业务场景 |

任何新设计都不应把名称、Logo 和小K处理成三套彼此无关的资产。小K的房屋体块、门洞标记、绿色空间块和变形路径，都应能追溯到家客来名称与现有 Logo。

## 3. 小K的标准形象基因

### 3.1 必须保留

- 厚实、阶梯式的房屋体块轮廓。
- 白色正面房体与绿色侧面/空间体块。
- 黑色圆润手脚，动作清楚且有重量感。
- 正面门洞标记，作为角色与“家”的核心识别符号。
- 简洁竖向眼睛和克制表情。
- 完整、稳定、容易缩小识别的剪影。

### 3.2 可以变化

- 手持工具：测距仪、客户档案夹、户型图、设计稿等。
- 姿态：引导、测量、整理、查看、展开空间、交付成果。
- 绿色空间体块的展开方式。
- 与业务场景相关的轻量服饰或配件，但不得遮挡主体轮廓。

### 3.3 不允许

- 把小K改成普通机器人、方块人或通用房屋吉祥物。
- 用播放三角形替代门洞标记。
- 随意改变白、绿、黑三部分的基本关系。
- 只显示头部或下半身，导致角色不可识别。
- 在同一页面同时出现多个不同画风、不同材质或不同比例的小K。
- 使用夸张幼儿化表情、漫画爆炸效果或廉价玩具质感。

## 4. F3 空间变形机制

小K的独特能力是：**从角色展开为空间，再从空间回到服务伙伴。**

这套机制应帮助用户理解真实产品流程：

1. 线索进入：小K整理客户与住宅信息。
2. 正式量房：小K拿起测距仪，绿色体块延展为测量路径。
3. 户型建立：角色轮廓展开为房屋框架或正式墙图。
4. AI 设计：户型从平面状态进入可感知的房间与材质场景。
5. 方案交付：空间收束为可查看、可比较、可继续操作的成果。

变形必须服务信息表达或状态变化，不能只是无意义的动画。产品没有对应能力时，不得用变形暗示该能力已经存在。

## 5. 小K的产品角色

小K在不同页面应承担明确、可说清的业务身份：

| 页面/场景 | 小K的角色 | 推荐动作或隐喻 |
| --- | --- | --- |
| 首页 | 空间服务向导 | 带领用户沿“线索—量房—设计”路径前进 |
| 线索列表 | 客户管家 | 整理客户档案、抽取资料卡、提示真实状态汇总 |
| 线索详情 | 客户项目陪伴者 | 打开该客户的住宅档案与当前服务阶段 |
| 正式量房 | 测量搭档 | 手持测距仪，引导进入正式量房 |
| AI 设计 | 空间转换者 | 将正式户型展开为房间与设计方案 |
| 结果/交付 | 成果交付者 | 展示已完成空间或引导下一项真实操作 |
| 空状态 | 友好引导者 | 解释当前为空，并指向唯一有效 CTA |
| 加载/过渡 | 空间构建者 | 使用 F3 变形表达处理中，但不虚构进度 |
| 错误状态 | 恢复协助者 | 说明问题并指向重试或返回，不做夸张沮丧表演 |

同一页面通常只选择一个主要身份。不要让小K同时扮演客服、设计师、测量员和营销代言人。

## 6. IP 融入界面的三层模型

### 第一层：识别

在启动页、首页主场景、TabBar 中央量房入口等位置，用小K完整形象建立稳定识别。

### 第二层：角色

让小K做与页面任务有关的动作。例如在线索页整理客户档案，在量房入口手持测距仪，而不是站在旁边挥手。

### 第三层：机制

让页面的信息结构继承小K的能力或所在场景。例如：

- 客户档案柜对应线索卡片和状态页签。
- 房屋路径对应客户从线索到量房、设计的阶段。
- 空间展开对应户型到设计结果的转换。

优秀的品牌化页面必须至少完成“识别 + 角色”；关键页面应进一步完成“机制”。只把小K贴在普通卡片旁边，不算完成 IP 融合。

## 7. C 版方向：业务实体隐喻

后续页面默认以线索页 C 版“客户档案簿”为方法论，而不是机械复制档案柜。

### 7.1 方法

1. 先确认页面的核心工作和高频信息。
2. 从真实家居服务场景中找到一个用户熟悉的实体、工具或工作方式。
3. 让这个实体隐喻同时承担视觉记忆和信息组织。
4. 让小K在其中执行一个与业务一致的动作。
5. 控件仍应保持熟悉、可点击、可阅读，不能为了概念牺牲效率。

### 7.2 已确认的线索页表达

- 页面隐喻：现代客户档案簿/住宅档案柜。
- 小K身份：客户管家。
- 状态筛选：档案索引签。
- 客户卡片：现代档案页，状态签与户型缩略图共同表达阶段。
- 摘要：跟进中的客户为主要信息，今日新增和已成交作为辅助信息。
- IP 分布：顶部摘要主场景一次，TabBar 中央量房入口一次；列表卡片不重复放置 IP。

### 7.3 对其他页面的要求

其他页面应复用“业务实体隐喻”的方法，但根据任务选择自己的载体：

- 量房页可以来自测量台、卷尺路径、空间标记系统。
- AI 设计页可以来自材料板、户型展开台、空间方案册。
- 项目进度页可以来自住宅施工夹、房间完成路径。

禁止所有页面都复制档案柜、文件夹和页签。统一来自角色、材质、色彩、几何与行为，不来自单一装饰物的重复。

## 8. 页面构图规则

### 8.1 操作型页面

- 业务任务优先于品牌展示。
- 顶部 IP 场景建议占首屏高度的约 18%–24%，不得形成压住列表的巨大宣传 Hero。
- 搜索、筛选、新增、状态切换等高频操作必须在首屏快速找到。
- 列表页在 `390x844` 基准视口内，除顶部结构外应尽量看到至少 3 条主要数据。
- IP 不应进入每一张业务卡片；使用一次强记忆点优于多次弱重复。

### 8.2 品牌/发现型页面

- 可以使用更强的空间场景和 F3 变形叙事。
- 首屏仍需呈现真实下一步操作，不能只剩品牌海报。
- 角色、空间和 CTA 应形成一条明确视线。

### 8.3 不对称与层次

- 默认采用有主次的不对称构图，避免平均分割的通用卡片仪表盘。
- 使用一处主要绿色视觉区域，其余由暖白、浅灰绿和真实内容承接。
- 可使用轻微纸张错层、房屋框架、档案索引、测量路径等有业务来源的层次。
- 避免无来源的光晕、玻璃、彩色网格和漂浮装饰球。

## 9. TabBar 与入口形象

- 保持五项结构：`首页 / 线索 / 量房 / 设计 / 我的`。
- 中间“量房”使用凸起圆形小K，完整显示身体并手持测距仪。
- 小K不能只剩头部、脚部或被圆形容器切断。
- 其他四项使用同一套圆角、中等线宽的线框图标。
- 当前项可使用浅薄荷底和品牌绿图标；其他项使用中性灰。
- 可在单个图标中融入门洞、JK 或房屋轮廓细节，但不得把每个图标都画成小K。

## 10. 色彩、材质与按钮

### 10.1 色彩

- 主色继续使用 `miniprogram/DESIGN.md` 和 `design-tokens.json` 中的品牌绿。
- 大面积背景以暖白、白色、浅灰绿为主。
- 蓝、紫、橙只承担业务状态，不扩展成新的页面主题。
- 每个标准页面最多保留一个强绿色主场景。

### 10.2 绿色按钮

主按钮不必局限为单一纯色，但必须保持克制和真实：

- 可以使用同一绿色色相内的细微自然渐变。
- 推荐亮面从左上到右下轻微变化，配合下方柔和投影。
- 可加入极轻的材质高光，但不能使用白色描边光圈。
- 禁止激光、霓虹、能量流、发光边缘和多色渐变。
- 按钮文字和图标始终保持高对比、清晰和稳定。

### 10.3 3D 与插画

- 使用清晰、干净、可识别的微缩家居 3D。
- 材质偏哑光硬质表面，边缘柔和但不能像通用黏土玩具。
- 场景光线自然，避免过曝白雾和无边界柔光。
- 角色必须和页面元素拥有一致视角、光源和阴影。
- 户型图、客户数据和业务结果必须来自真实数据或明确的设计示例，不能把生成图当作生产内容。

## 11. 功能真实性

品牌设计不能扩大产品能力：

- 先读取当前页面代码、模块清单、接口和已有状态。
- 不得加入没有跳转或数据来源的日程、提醒、AI 推荐、快捷联系、进度预测等功能。
- 设计稿中的统计项必须能对应现有数据；示例数据只用于表达排版。
- 正式户型缩略图必须来自正式 version-4 wall graph 的读模型或真实外部预览。
- 设计方向已批准不等于已开发；实施状态必须在模块清单中单独确认。

## 12. 新页面设计流程

每次新建或重设计小程序页面时：

1. 阅读 `AGENTS.md`、`miniprogram/DESIGN.md`、本文以及受影响页面的模块清单。
2. 检查当前代码和现有 UI，列出必须保留的功能、状态、数据和跳转。
3. 先从花瓣搜索，再补充至少两个相关的当前移动产品或专业设计参考。
4. 为小K定义一个明确业务身份，不得只写“装饰”或“吉祥物”。
5. 定义一个来自真实业务的实体隐喻，并说明它如何影响信息结构或交互。
6. 默认沿用 C 版方向的品牌强度：一个主要 IP 场景、一个结构化品牌机制、其余区域以业务效率为主。
7. 先输出高保真设计稿并等待用户明确批准；没有“开始开发”“开始实施”或“按此方案落地”，不得修改产品代码。
8. 获得实施批准后，严格使用现有设计 Token、真实功能和当前模块契约落地。

设计交付应能回答：

- 小K在这个页面是谁？
- 它正在做什么真实工作？
- 哪个信息结构继承了品牌概念？
- 如果移除小K，页面是否仍然可用？
- 设计是否暗示了不存在的功能？

## 13. 反例清单

- 普通白卡列表上随意贴一张小K插画。
- 为了显得有 IP，在每条列表、每个按钮、每个空状态重复角色。
- 用巨大品牌场景挤压核心操作与真实数据。
- 把所有页面做成同一种文件夹或房屋卡片。
- 使用 AI 感强的玻璃面板、荧光绿描边、激光按钮或无意义渐变。
- 让小K替代业务图标，导致导航含义难以识别。
- 为了画面丰富加入未实现入口或不可点击模块。
- 让角色遮挡文字、被容器裁切或在小尺寸下失去门洞与体块特征。
