### 3.2 Principal, conversation, and content protocol

```ts
type Principal =
  | { kind: 'user'; userId: string }
  | { kind: 'admin'; adminId: string };

type ResourceRef = { type: string; id: string }; // Registered types only; not arbitrary resource access.
type MessageContentV1 = {
  version: 1;
  blocks: Array<
    | { type: 'text'; text: string }
    | { type: 'citation'; citationId: string; fallbackText: string }
    | { type: 'notice'; code: string; fallbackText: string }
  >;
};
type InvocationOwner =
  | { kind: 'generation'; generationId: string }
  | { kind: 'assistant_run'; runId: string }
  | { kind: 'knowledge_job'; jobId: string };
type RunTrigger =
  | { kind: 'user_message'; messageId: string }
  | { kind: 'domain_event'; eventId: string }
  | { kind: 'scheduled_task'; occurrenceKey: string };
```

Serialize bigint IDs as decimal strings and timestamps as UTC ISO-8601. Display/scheduling timezone is explicit, defaulting to `Asia/Shanghai` for this project. Persist `schemaVersion` with protocols/snapshots. Unknown message blocks render safe server-provided `fallbackText`. Future media/actions reference resources resolved to short-lived authorized URLs/allowlisted actions; never persist permanent signed URLs, HTML, or arbitrary scripts as the message contract.

One person may have customer/staff identities, but each request uses one selected valid identity. Switching cannot carry internal knowledge, preview conversations, or staff tools into customer sessions. System/AI are author types, not login identities or permission bypasses.

P1 production permits only `user_message` run triggers. Later internal services enable event/scheduled triggers; clients never choose them. Reserving `RunTrigger` now avoids fabricated user messages for digests/reminders. `TextModelGateway` returns normalized text, attempt ID, finish reason, and available usage/provider request ID. Compatibility wrappers support old string adapters; missing usage is not zero. Future streaming may add run-event endpoints without changing final message/citation commit contracts.

## 4. Data model

### 4.1 Common constraints

All new business tables have non-null `enterprise_id`, primary key, and creation time; mutable tables have `updated_at` and optimistic `version`. Enable RLS and existing tenant transactions. Tenant-table relationships use `(enterprise_id, id)` unique keys and composite FKs to prevent cross-enterprise ID composition.

`users` is an existing global identity. Its `enterprise_id` need not equal a consultation enterprise; access derives from signed identity, validated entry, and participation. `admin_users` and business-resource tenancy must match. Polymorphic `ResourceRef` cannot rely on an ordinary SQL FK for existence: registered adapters validate on binding and use. It does not replace real business-domain FKs.

## 5. API contract: implemented scope is defined by the section2 1A/1B delivery records

### 5.1 Common rules

- Success: `{ success: true, data, requestId }`; failure: `{ success: false, error, code, requestId }`. String IDs, explicit versions, cursor pagination. Errors never reveal credentials, raw system prompts, or another tenant's resource existence.
- Repeatable writes, including create/send/retry/index/publish, require `Idempotency-Key`, scoped by enterprise/principal/operation/key and retaining request hash/result reference. Same key/body returns original result; different body returns 409. For send, key equals `clientMessageId`; cancel/archive/update use their own request keys.
- Edit/publish/archive require `expectedVersion` or explicit `expectedEditVersion`; conflict is409. Enterprise message storage caps at4,000 characters; rendered knowledge caps at16,000 characters/48,000 UTF-8 bytes. Retrieval/prompt budgets are in section2. Exceeding them fails explicitly without silently truncating original submissions.
- Clients submit user text and allowed parameters only, not system messages, tool results, model names, roles, enterpriseId, or final citations. Models cannot decide authorization fields either.
- Transport and content versions are separate. Add compatible fields; use a new version/endpoint for breaking changes without requiring old clients to interpret new actions.

## 7. Knowledge and answer flow

### 7.1 Publication and retrieval

1. Maintain FAQ/body drafts with source, category, audience, validity, and actor.
2. Index asynchronously with stable chunking, hash, embedding model/dimension/profile; independent embedding job audit.
3. Authorized tenant preview may select ready drafts; customers receive current published/effective versions only.
4. Publish atomically switches version/epoch with expectedVersion. Late old jobs cannot mark an obsolete hash ready.
5. Constrain candidates by tenant/audience/version/validity before keyword/semantic ranking, then revalidate outputs. Never retrieve across tenants and ask the model to filter.
6. Cache keys include tenant, audience/authorization fingerprint, epoch, profile, and query hash. Future personal data adds principal/resource authorization versions. No global query-only cache.

Section2 records pgvector, separate Embedding and answer/preview verification. Formal knowledge-version/authorization contracts now drive answering; original database cutover remains pending. Chinese lexical retrieval uses versioned segmentation/synonyms/bigrams rather than default full-text configuration. [Official pgvector documentation](https://github.com/pgvector/pgvector) describes combining vector and full-text retrieval.

### 7.2 One answer

`Authenticate/resolve enterprise → conversation/quota checks → persist message/run/job → load valid history → retrieve authorized evidence → model call → validate answer/citations → recheck context/access → atomically persist final message/run terminal`.

- Pass relevant excerpts only with explicit data boundaries. “Ignore instructions” or “invoke tools” inside documents is source content, not system authority.
- Structured output includes answer, answerKind, and citation IDs restricted to the retrieved set. ID validation proves source membership, not semantic correctness; use real-question evaluation and conservative answer policy.
- Enterprise services/policies/prices require evidence; explain missing evidence and use existing contact paths. If enabled, distinguish general renovation advice from enterprise commitments; P1 focuses on enterprise answering.
- Models cannot confirm fees, schedule commitments, structural changes, or acceptance. General policy does not become a final customer-specific promise.
- If conversation/knowledge epoch changes during generation, revalidate evidence and suppress invalid results. Bound retrieval/regeneration retries; return safe `context_changed` when budget is exhausted, not an infinite loop.
- New answers use current knowledge over old conversational conclusions. Mark old answers with historical versions. After withdrawal/access tightening, subsequent reads omit restricted excerpts and dependent answer bodies, projecting unavailable content; invalidate summaries/caches. Already displayed/copied content cannot be remotely recalled.

## 8. Concurrency, retries, and future modes

### 8.1 Run state machine

```text
queued -> running -> succeeded
queued -> cancelled
running -> failed | cancelled | indeterminate
failed | cancelled -> new run (retry_of_run_id), never resurrect original
indeterminate -> reconcile/terminate, or explicitly acknowledge unknown outcome before a new run
```

On send, lock conversation and atomically validate idempotency/state/active run/quota reservation, allocate seq, and insert message/run/job. Busy 409 inserts no message. Concurrent sends, double taps, and offline replay have deterministic results.

Workers claim leases and revalidate before execution/completion. Commit message, citations, terminal state, usage settlement, and outbox atomically before notifying clients. A crash after provider response but before commit requires recovery based on queryability/proven nonacceptance. Unknown acceptance becomes `indeterminate`, not automatic second charging. Stale lease tokens cannot complete; late results cannot override cancellation/takeover.

Transient errors proven unsubmitted may retry with bounded backoff; accepted unknown requests cannot automatically switch providers. Track retry IDs, request fingerprints, and provider attempts. Business idempotency does not imply exactly-once external cost.

### 8.2 Future takeover and proactive service
