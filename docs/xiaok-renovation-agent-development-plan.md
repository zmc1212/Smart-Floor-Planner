# 小K装修 Agent 开发计划（第一版）

> 2026-10-27建立，2026-10-31按用户最新要求收敛第一版范围。本文仍是小K开发的**唯一计划和任务入口**，第2节是唯一当前交付记录。
>
> **第一版：小K结合企业知识库对话，按真实装修阶段向业主、工人、设计师、老板提醒工艺标准，并为四端生成日报；能看云工地、围观和设计师。** 用户已明确：围观就是云工地直播的公开访问场景，第一版需要实际能看直播。云工地与公开围观是一项能力，按访问权限区分，不另建一套直播产品。
>
> 本次范围取代旧“六项P0全部完成→D1–D7完整方案”的推进顺序。旧实现、批准设计、失败次数、未知结果、费用与证据保留，第9节只用于查证，不再调度工作。设备托管下单界面设计暂停；现按用户开发指令实施，实际结果以第2节为准；生产部署仍单独授权。

## 1. 第一版交付什么

**让小K成为企业知识库支持的装修沟通助手：能解释、能在当前阶段提醒、能按实际记录生成日报。** 四端指同一产品中业主、工人、设计师、老板四种角色的入口和权限视角，不新建四套Agent或四个独立应用。

| 能力 | 第一版可用结果 | 依据与范围 |
| --- | --- | --- |
| 小K对话与装修答疑 | 业主用自然语言问装修知识，能连续追问、补充条件、改口；其余三端也可在获权范围内问相关工艺与项目问题 | 主要依据本企业已发布、当前角色可见的知识库；回答解释原因、适用条件和注意事项，出处可打开。一般建议、企业标准、现场事实和待核实内容分开；无企业依据时如实说明，不编造企业规定 |
| 四端阶段工艺提醒 | 项目进入对应阶段后，四端分别收到与自己有关的工艺标准、核对要点和待办，并可继续问小K | 项目真实阶段与有效成员关系确定对象，企业知识确定标准。阶段未知先确认，不从聊天、日期或摄像头画面猜测进度 |
| 四端日报 | 用户可要求小K生成当天日报，看到对应角色的实际进展、待处理事项和阶段注意点，退出后可重看 | 基于获权项目记录生成并保存；没有记录就说明缺项。第一版先支持按需生成，定时生成/推送不是本版前置条件，不因此新增自动化运营平台 |
| 云工地直播（含围观） | 业主查看本人获权工地直播，访客围观明确获准公开的工地直播 | 共用云工地设备与播放基础；本人访问和公开围观分别校验授权。必须实际播通，照片、播放器空壳或模拟视频不算直播完成 |
| 看设计师 | 查看已公开的设计师资料和作品，可回到小K继续咨询 | 复用现有设计师/作品入口及发布权限，不扩展复杂匹配、营销自动化或分佣流程 |

### 四端分别收到什么

| 角色 | 阶段提醒 | 日报内容 | 可见边界 |
| --- | --- | --- | --- |
| 业主 | 本阶段要了解和确认的工艺标准、准备事项、验收关注点，用生活语言解释 | 本人项目今天已发布的进展、需要本人确认/准备的事项、下一步已确认安排 | 仅本人获权项目、业主可见知识和明确发布的记录；不含工人内部草稿、内部讨论或其他客户资料 |
| 工人 | 当前项目/工种相关的施工做法、操作前核对和自检要点 | 本人及所在有效项目中允许查看的施工记录、待补充/待核对事项、当前工艺要点 | 沿现有有效项目成员和原记录权限；共享现场对话不等于共享业主私聊，也不自动扩大商业信息权限 |
| 设计师 | 当前阶段的图纸、材料与工艺衔接检查，以及需要设计师核对的问题 | 获权项目当天进展、待设计核对事项、已记录决定及对后续施工的影响 | 仅被分配/获权项目和允许查看的企业知识；不跨客户、项目或企业取资料 |
| 老板 | 获权工地的阶段风险、尚待核对的标准执行事项与需协调的问题 | 企业内获权工地的真实进展、未处理事项、责任与协调线索，可下钻原记录 | 继承现有企业管理边界；admin/super_admin在所选企业继承负责人业务权限，不读取无授权的业主私聊 |

同一知识标准按角色解释，不复制成四个知识库。“提醒过”“看过”“记录了”均不等于施工达标、实际完成或工程验收。

### 第一版暂不扩展

设备租赁/托管下单、报价收费、押金退款、安装售后商业流程，完整设计方案审批/变更闭环，复杂经营分析，广泛图像识别/精确量测和语音能力扩展，均不作为第一版交付条件。已有功能和记录保留；若现有安全缺陷会影响第一版路径，仍须修复，不能以移出范围绕过。刚才拟做的D7业主下单设计不继续。

模型联网搜索、显式缓存、受控前缀续写和离线Batch不再全部作为本版统一前置；只保留第一版真实依赖的稳定对话、必要工具协议、知识检索、持久任务、权限、恢复和用量机制。不为首版重开框架或模型横向比较。

## 4. 开发顺序与有界验收

顺序为 **V1-01知识对话 → V1-02四端阶段提醒 → V1-03四端日报 → V1-04云工地直播（含围观）与设计师入口收口**。这是同一第一版的四项用户交付，不为每个补丁新设阶段。已有完整证据直接复用；每项有真实入口、可见反馈、持久重进、权限和失败恢复。相关交付完成后按项目规则提交并继续后继，不等待例行手测或截图批准。

### V1-01：业主能正常向小K问装修知识

**交付：** 优先把企业知识问答做可靠。小K理解整轮问题，结合可见的企业资料说明工艺原因、条件和取舍，能承接“为什么”“我家是另一种情况呢”。问题不依赖填写预算或确认需求表才可回答。未关联项目仍可问企业公开给该角色的知识；项目事实和阶段未知时只确认必要信息。

**固定旅程：**

1. 业主询问装修做法，逐步补充房屋和使用条件、再改口追问；答案随条件调整，企业依据可打开，退出后能回看同一问答与有效出处。
2. 围绕同一条工艺标准检查四端允许/不允许看的内容，并覆盖其他企业、资料撤回、没有对应资料和一次真实检索失败后的明确恢复。预期动作放在断言中，不教测试用户命名工具或提供标准答案。

四端知识不足时准确说明缺项，不能用固定拒答代替整项正常咨询。文字主链若仍遇到原D2安全缺陷，按第6节处理，不能靠排除失败样本完成。

### V1-02：到了装修阶段，四端收到各自的工艺提醒

**交付：** 复用企业当前节点配置（默认前期、设计、拆改、水电、泥木、油漆、安装、软装、完工、入住），由获权人员实际更新的阶段/节点事件触发。企业标准按具体工序、适用条件和角色筛选；防水等细工序映射到企业的实际配置，不另造互相冲突的进度。

每条提醒带项目、阶段、适用角色、有效知识来源与需要本人核对的事项；四端能从提醒继续问小K。离线期间事件持久保留，同一事件/版本/接收人不重复投递。阶段纠正、成员移除、知识撤回后，尚未发送及重进打开的提醒都须重新核权；不能把旧提醒继续当有效要求。

**固定旅程：**

1. 一个合成工地真实切换到水电阶段，业主、工人、设计师、老板各看到相应提醒，内容来自本企业已发布标准，能够追问并返回原资料；未获权人员与其他企业不可见。
2. 覆盖泥木中的防水工序和安装节点的适用差异；更正阶段、重复事件、离线重进、撤回标准、移除成员及一次投递失败恢复，均不重复、不串项目、不残留有效旧权限。提醒不证明现场实际达标。

### V1-03：四端都能生成有事实依据的日报

**交付：** 用户用自然语言请求“给我今天的日报”等即可生成。按`Asia/Shanghai`自然日、项目与角色确定范围，区分当天实际记录、已发布结果、待核对/待处理事项和已确认后续安排。企业知识可解释本阶段关注点，但不能替代当天施工事实；标准建议与实际完成分开。

日报保存日期、项目/企业范围、受众、生成时间和原记录/知识版本；重进能打开，权限与来源变化后不能继续泄露原内容。同一请求重试不重复生成，同一日期事实更新可生成明确的新版本，不静默篡改旧报告。老板沿现有权限汇总多个工地；没有记录时写明“暂无已记录进展”，不写成未施工或已完工。

**固定旅程：**

1. 至少两个工地形成真实差异，包含已发布记录、内部待核对内容和待办；分别从四端生成、保存和重进日报。业主不看到内部草稿，工人/设计师只看获权范围，老板能从汇总下钻原记录。
2. 当天没有新记录、补发/更正记录、相同请求丢响应重试、生成失败恢复、成员撤权和资料撤回时，报告内容、版本、访问与原记录保持一致；不编造施工量、人员到场、验收、金额或完成承诺。

### V1-04：同一云工地直播支持本人查看和公开围观，并能看设计师

**交付：** 云工地是一项直播能力。业主按本人项目权限进入；对明确允许公开围观的工地，访客通过围观入口观看同一工地获准公开的直播画面。复用现有设备、流媒体与播放基础，不再单列“公开直播产品”或要求先实现设备商业托管。已有可用回放保留，不新增一套录像存储/计费服务作为首版前提。

围观沿现有公开工地合同完成必要授权与审核，明确可公开的摄像头/画面；未允许公开的设备、私有记录和业主私聊不随工地公开。成员撤权和取消公开分别使相应旧入口/会话/媒体失效。无设备、设备离线、直播失败如实呈现并可恢复，不能用成功提示或照片代替直播。

设计师沿既有公开主页和作品浏览入口，内容撤回即时受限，能返回小K继续咨询；不扩展为新的接待、预约或分佣系统。

**固定旅程：**

1. 同一实际可用测试工地：业主打开本人直播，访客在未公开时不可看；获权人员批准该工地围观后，访客实际播放公开允许的直播。移除成员、关闭围观及重进分别验证对应旧授权失效；覆盖离线/断流与恢复。
2. 查看已公开设计师和作品，进入/返回小K保持上下文，撤回作品后旧入口受限；不创建重复客户或改变来源归属。

真实视频源和必要公开授权缺失时，明确缺少什么、影响哪条路径；其他三项继续开发，但第一版云工地能力不能标为完成。设备采购、外部服务购买和生产启用仍须原有授权。

## 5. 实施边界

1. **一套Agent、一套企业知识库服务。** 复用当前LangChain/LangGraph、模型适配、工具协议、持久任务、幂等、用量与恢复。扩展前只核对相关维护中实现、测试和供应商已知问题；有具体缺口才改，不重写平台。
2. **标准与事实分开。** 企业标准来自有效知识，项目进度/施工记录来自原服务；不能因符合标准措辞就判定现场合格，也不把直播画面自动送模型做工程质量结论。正式v4墙图只读消费，不写回旧layout副本。
3. **四端按身份与项目授权裁剪。** 企业、知识受众、本人项目、有效成员、公开围观各守原边界；公开工地不意味着公开聊天、日报或其他摄像头。管理者继承和明确所选企业的规则不变。
4. **提醒和日报依赖真实持久数据。** 复用outbox/Worker及现有通知渠道；先确保站内可见与重进。微信授权或渠道不可用时如实保留站内结果，不伪称微信已送达，不为首版购买新推送渠道。
5. **设计沿已有批准源。** [双语还原台账](./miniprogram-design-restoration-ledger.zh-CN.md)/[英文](./miniprogram-design-restoration-ledger.md)与现有组件为基准。同一聊天中的标准提醒/日报话题优先复用共享状态规则，不为每种文案画一页。真正新增视觉/交互才先设计并取得明确实施批准；下单设计暂停不阻塞已有聊天的知识服务。
6. **测试、费用与部署权限保持。** 只用授权开发/隔离库和明确标记的合成数据；不污染生产。原生沿Stable DevTools、官方SDK、单控制器、原锁与窗口核验，不用Computer Use、不抢资源。模型调用不新增预算，unknown和历史费用保留；生产上线单独授权。

## 6. 验收与失败处理

- 只按当前V1交付的实际依赖测试。实现时做定向单元/客户端检查，集成后做真实服务与权限/撤回/幂等，再做受影响的Stable原生整链；不先重跑旧全套，不把前缀续写、Batch或全PPT能力恢复成首版门槛。
- 用户旅程使用自然语言，包含追问、信息不全、更正、重进和实际服务失败；预期动作和安全断言放在测试里，不放进用户提示。新建或实质改变的语义核心每条固定两次已配置模型首稿，保留原始失败，不采到通过为止；沿现有授权和原账册执行，不因计划改名追加额度。
- Agent语义交付至少一条核心旅程从小程序实际输入，经真实配置Worker到实际结果与持久重进；不能预置回复或只验SDK。提醒/日报要验实际写入与回读；云工地要验真实媒体播放。有效且未变化的历史证据直接复用，记录来源/依赖/配置绑定。
- 触达范围始终保留租户、角色、有效成员、知识/媒体撤回、版本、重复/并发请求和失败恢复检查。缺数据就在授权测试库创建合成夹具，不只验空页面。完成后同步受影响双语模块合同；未变UI不升级还原状态。
- 同一业务期望两轮修复仍失败，停止第三次同类提示词/关键词补丁。保留期望与实际I/O、原尝试和费用，在既有二期合同说明归属、共同原因假设与能区分假设的机制检查。旧D2次数2跨新V1编号保持，不能通过缩范围、改断言或重命名伪造通过。
- Knowledge证据不正确修Knowledge；Evidence正确而编排/回答错误修Agent。安全/来源撤回/虚假结果缺陷阻塞受影响路径；真正独立的其他交付可串行继续，在第2节记录返回条件。环境或设备不足不通过重复调用制造进度。
- Stable资源忙时等待或做独立实现，程序化释放自己取得的资源。真机、BLE、真实微信登录等未覆盖条件如实记录，不要求例行用户手测，不把沉默当通过；直播媒体未播通仍是直播能力的未完成项。

## 7. 第一版怎样算完成

以下同时成立才交付第一版，不能用总测试数量或后台内部进度代替：

1. 业主能从实际小程序入口向小K自然问装修知识，围绕本企业有效资料得到有依据的回答并连续追问，出处/历史可重进，缺资料与失败能正确恢复；其余三端的相关提问守住原权限。
2. 同一工地真实节点变化后，业主、工人、设计师、老板分别收到适用于自己的企业工艺标准提醒，能继续追问，重试不重复，撤权/撤回后停止相关访问与投递。
3. 四端能按权限生成并重看当天日报，老板能区分至少两个工地的实际情况；记录、待办、建议和未知项表达准确，原记录可追溯。
4. **同一云工地直播能力**支持业主本人查看与获准公开后的访客围观，真实视频播放、重进、关闭公开/成员撤权和失败恢复有证据；设计师资料/作品可浏览并回到小K。

第一版完成只代表上述软件范围成立，不代表完整PPT、旧D1–D7所有目标、工程验收或生产上线。某项受阻就如实保持`Limited`并指出影响范围；已实现功能继续保留，不抹掉原未验和失败。
