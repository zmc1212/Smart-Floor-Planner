## 1. 最终要做成什么

**做成一个懂装修、能围绕同一客户和项目持续办事的小K。** 客户用生活语言交流，小K回答问题、理解需求、查阅获权资料、提出需要确认的行动，调用真实业务服务，并把后续结果带回来。设计师、施工人员和负责人各自完成需要人决定的部分。

产品依据为[《家客来小K装修服务功能方案》](./装修施工标准手册制度规范/家客来小K装修服务功能方案.pptx)：第1–39页主方案，第40–88页为对应界面放大附页。本次已核对全部主方案文字及附页对应关系；这不构成新一轮视觉还原验收。原文件 SHA-256：`9221a83057fb1b2aa691ecde6cf60a0aa2dfb0d352aad4b6eab2cb6f15209af4`。

最终用户应能完成这些事：

- **客户先聊起来：** 预算没定也能咨询；已说过的不反复问，能改口、换话题、发图片和语音，得到适合自家情况的解释与参考方向。
- **需要真人时接得上：** 从设计师分享、公司渠道或公开工地进入自己的咨询，设计师带着原话、图片、需求和待核实事项继续聊，不要求先交手机号或填完摘要。
- **进入施工后继续服务：** 查自家实际进展，水电、防水、铺砖、安装前只补必要信息，时间或方案没确认时不替团队承诺。
- **现场少重复录入：** 工人在项目共享对话发图文或语音，小K整理草稿，获权人员核对发布，设计师能找到对应房间、图纸和客户需求。
- **事情有后续：** 客户说“有新照片告诉我”，以后确有新记录时能收到；方案更改、费用、工期、落实和关闭各有真实决定与记录，老板可按项目查看待办、追问和协调。
- **云工地服务完整：** 有真实设备及供应商条件后，按项目授权看直播/回放，开通、报修、延期、退场和押金处理可追踪。

衡量进度用“新增了哪项用户能完成的事”。框架接入、测试数量、模型首稿分数、补丁编号都不能单独算业务阶段完成。

## 4. 开发顺序与每项交付

执行顺序为 **P0基础能力补齐 → D1 → D2 → D3 → D4 → D5 → D6 → D7**。P0是D1内部最高优先级前置包，不是新的用户业务阶段。D1–D7每项都包括已有小程序入口、真实服务、可见反馈、持久重进、权限和失败恢复。后端内部进展不能单独关闭阶段。每项先补缺失行为，再执行该项验收；已完整覆盖的部分直接复用证据。

### P0：优先复用成熟实现，补齐模型基础能力

**优先级最高：本包收口前不启动新的下游整轮业务验收。** 目标是形成可使用、可恢复、可观测的模型能力链路；控制台支持勾选、安装了依赖、接口返回200或个别样本通过，均不等于完成。

**先复用再定制。** 之前实际对照的三套是AnythingLLM、LangChain官方`createAgent`、PydanticAI，见[原OS-CONTRACT-03三框架隔离对照记录](./xiaok-assistant-phase-2.zh-CN.md)。固定试验中三者完整链各0/2，不能归因为三个框架均无能力；记录已指出共用需求更新、授权/回执接缝和模型错误。当前小K使用LangGraph `StateGraph`和LangChain类型工具，模型请求、主循环及最终答复校验仍有定制，不能称为已采用完整`createAgent`运行时。

每项先在本节明确原生实现入口、实际采用部分、保留的业务扩展及必须自研的理由；优先检查现有LangChain/LangGraph的模型适配、工具结果反馈、结构化输出策略、中间件与中断恢复，复用已保存失败trace作判别，不重跑三框架宽矩阵。框架能直接提供的通用机制优先调用现成实现；租户/来源撤回、业务事务、真实回执、审批、幂等和未知用量继续由现有服务守住。整体迁移或重写仍需具体收益与边界兼容证据，不因本次优先级调整自动启动。

**实际采用与定制边界（2026-10-27）：** 已核对已安装框架源码及上游[工具实现](https://github.com/langchain-ai/langchainjs/blob/main/libs/langchain-core/src/tools/index.ts)/[工具测试](https://github.com/langchain-ai/langchainjs/blob/main/libs/langchain-core/src/tools/tests/tools.test.ts)。通用参数校验直接调用原生`tool`，使用无副作用回调且只捕获`ToolInputParsingException`；已有LangGraph负责有界循环。原生`response_format`通过现有审计传输接入，未宣称使用完整`createAgent`或自动provider策略。供应商Batch/Partial/Web参数不属于现有core工具的通用机制，保留薄HTTP适配；持久任务只补原schema无法表达的远程batch/file/custom_id、不可变快照及预留，复用原tenant transaction、manager guard、provider attempt及清理机制，不复制租户解析、业务审批、事实或引用管线。

### D1：自然咨询能继续，需求更正能可靠落地

实施重点：保留现有审批和服务守卫，把整句关键词拦截改为可组合的Agent回合；短期原话、当前需求及工具结果进入正确上下文。完成后，在授权开发企业内让普通C01入口走这条能力，不再只存在于手工标记的测试会话；保留可回滚开关，生产默认不切换。

**固定验收旅程：**

完成后新增的可用动作：**客户可以正常聊装修，并在同一会话里安全修改需求。** 后继D2。

### D2：能给专业解释，也能看懂问题所带的图文

**对应PPT：5、6、14、15、18、19、23、38的答疑部分。入口：C01及既有来源面板，后台现有知识管理。**

要交付：围绕房屋、收纳、用电设备、材料和施工准备，结合已有企业资料解释原因、条件、选择和影响；能承接“为什么／换个位置呢”。客户直接发图片，Agent实际读取本轮获权图片，并结合已有需求及正式v4读模型；歧义时只问必要问题。

实施重点：复用知识发布和检索，按本阶段问题补少量所需资料，修正文丢失、定位错误或条件匹配问题。一般专业建议、企业规定、本人项目事实、图片观察与未知项分开表达。单图不能确认承重、隐蔽质量或精确尺寸；项目事实不足时继续回答有依据的部分。外部厂家网页只是确有必要时的一种资料源，不要求每次回答凑齐厂家PDF、网页和企业知识三套来源。既有真实来源/引用缺陷仍保留，相关路径未修复前不宣称支持。

**固定验收旅程：**

1. 一次生活问题带出企业做法和条件，客户追问并更正条件；答案解释取舍、出处可打开，相关来源撤回后不可继续引用旧结论。
2. 同一客户发真实测试图片/获权户型，问空间或设备安排，再换位置追问；图像确实传入，已知与待核实内容准确，不串房屋，不把参考图写回正式墙图。

完成后新增的可用动作：**客户获得贴合上下文的装修建议，并能继续问下去。** 后继D3。

### D3：获客、围观与设计师接续成为一条客户旅程

**对应PPT：2–13、39；7–9的公开视频依赖D7。入口：现有设计师主页/作品、公开工地、C01及员工S01接待。**

实施重点：先串联现有作品、公开记录、接待与客户服务，补缺失的AI案例文案/分享材料辅助，仍由员工核实发布。来源、接待人、负责人和分佣分开；接待不自动改变分佣。等待/接管期间AI按原模式暂停，取消可回AI，不强制提供电话；电话联系另行同意。普通沟通时间在聊天商量，不新建沟通预约系统。

**固定验收旅程：**

1. 分别从设计师分享和公司渠道进入，咨询或围观后找设计师；员工接手沿用资料，入口来源正确且不重复建客户/改变分佣。
2. 客户不提供手机号也能申请接待、等待和取消；接管后无迟到AI。公开内容撤回或接待权限撤销后，旧引用、图片和资料立即受限。

完成后新增的可用动作：**客户从内容进入咨询，真人带着资料继续服务。** 后继D4。

### D4：进入工地后，客户、师傅与设计师围绕同一件事协作

**对应PPT：13、16–23、26、33、37、38。入口：客户C01、云工地、施工S04、员工资料与方案入口。**

要交付：客户问“现在做到哪里／这个位置能不能改”，Agent读取本人项目的真实阶段、已发布记录、需求和有效图纸再解释。师傅在该项目共享对话发图文，Agent整理草稿，获权人员核对后发布；底盒等现场问题能连到相应房间、图纸和需求，由设计师核对处理。

实施重点：复用项目成员/节点、记录发布、资料适配和事项服务。每个工地一份团队共享对话，业主私人咨询独立，只收到明确发布的内容。计划、实际、发布、验收分开；缺少房间对应关系时澄清，不靠同名猜测。改方案走真实版本及负责人/客户决定，不通过聊天文字直接批准施工。

**固定验收旅程：**

1. 经理更新实际阶段，客户询问该阶段的准备；师傅上传照片和文字，草稿核对发布后客户在原咨询收到真实进展，重进仍能打开原记录。
2. 师傅提出一个底盒位置问题，设计师找到该房间资料并回复，客户看到可见的具体版本；内部草稿、其他项目资料和已移除成员访问均被隔离。

完成后新增的可用动作：**一条现场问题能从师傅传到设计师，再有依据地反馈客户。** 后继D5。

### D5：关注会跟进，关键决定会落实，负责人能追问协调

实施重点：复用outbox、关注、事项状态、正式方案和OPS-01简报，补事件与角色之间缺失的接续。至少用两个工地形成真实差异，不把重复生成摘要当作经营服务。时间未确认不宣布到场或逾期；新版本不能继承旧同意；客户同意不等于施工完成、工程验收或付款。微信通知沿已有渠道和授权，无渠道时如实保留站内消息，不伪称微信已送达。

**固定验收旅程：**

1. 客户关注照片，页面关闭后团队发布新记录，客户重进能看到同一事项更新；取消、换节点和撤回分别阻止不应投递的旧消息。

完成后新增的可用动作：**小K能把交代过的事继续跟下去，负责人可按事实协调。** 后继D6。

## 5. 实施边界

1. **保留一套Agent与业务内核。** 沿用LangChain/LangGraph、当前模型适配、持久任务、幂等、用量和接管协议。扩展时只查与当前缺口相关的维护中实现、测试和供应商问题；没有具体收益不迁移框架，不再启动大范围产品/模型比较。
2. **业务约束守住动作，理解能力覆盖整个问题。** 权限、版本、参数、审批、金额/状态回执由服务端校验；不能靠“预算／照旧”等关键词替代整轮意图理解，也不能用固定回复掩盖吞题。模型不直接授予权限、批准方案或宣布尚未发生的写入。
3. **知识和项目事实各守来源。** 企业知识通过现有服务发布和撤回；现场事实实时读原业务服务，正式v4墙图只读消费。记忆帮助理解，不创造第二套客户/项目事实库。
4. **已有设计直接复用。** C01、C02、S01、S04等按[当前设计台账](./miniprogram-design-restoration-ledger.zh-CN.md)的唯一最新批准源；主屏、重要变体和共享状态规则足够即可实施。普通话题不重新设计一页。真正新增交互/视觉才先出具体方案并取得批准。原图853×1844按宽映射390×844；不得切片铺成产品UI。
5. **环境与操作边界保持。** 只用已授权开发环境和清楚标记的合成数据；租户、本人/项目成员、来源撤回及管理者继承不能放宽。原生测试复用Stable DevTools和官方SDK、单控制器及原锁；沿已有“不用computer-use”的约束，不抢窗口、不建临时项目。未知结果不自动重放；生产发布、购买外部服务和新增商业承诺仍需明确授权。

## 6. 验收有边界，开发不围着失败样本打转

### 每项只做服务于当前交付的检查

- **P0前置优先：** 先完成第4节基础能力包；此前只执行服务于该包实现的必要定点检查，不新开D1–D7整轮模型/原生验收。用户“不追加模型调用”继续有效，不能改以模型协议探测或Batch名义增加调用。本次计划修订不操作主线程进程、资源锁或配置。
- **先开发后收口：** 开工先说明用户动作、已核实缺口、这次要改的行为及完成检查。不要把“先跑一遍所有旧测试”当作下一步。
- **范围预先固定：** 以第4节每项的两条用户旅程为语义核心，用自然表达、逐步补充、改口和真实失败；预期动作/答案写在断言里，不塞进客户提示。新建或实质改变的语义核心，每条固定两次配置模型首稿；记录所有原始结果，不采到两次通过才停。D7等纯确定性接入不额外调用模型。
- **分清证据：** 单元验证机制，真实服务验证数据库与权限，原生验证真实入口和反馈。涉及Agent语义的交付，至少一条本项核心旅程从小程序实际输入，经实际配置模型Worker，到业务结果与重进贯通；不能预先塞提案、替换模型答复再当作实模体验通过。纯SDK与服务分开通过时明确仍缺整体证据。语义行为未变且整链证据有效时可复用，不重复跑；纯确定性功能只验证其真实客户端/服务链，不为它补模型调用。
- **检查不能省的边界：** 对本次触达范围验证真实写入/回读、权限和来源撤回、版本/幂等、失败恢复；只读回答验证消息与依据的持久恢复。没有数据就用批准开发/隔离库的合成夹具，不验空页，也不种生产数据。
- **完成就推进：** 相关代码、固定旅程、必要兼容/安全检查、双语模块记录和本地相关提交完成后更新第2节，继续后继。真机、BLE和真实微信授权等未覆盖范围如实记录，不变成例行用户手测任务；关键范围未通过仍不能标为完成。

### 失败怎样处理

| 情况 | 必须采取的动作 | 不应继续做的事 |
| --- | --- | --- |
| 第一次失败，根因可定位 | 保存原始I/O；判断是Agent、Knowledge、业务服务、驱动还是供应商；优先用旧trace/确定性检查定位后修复，只复测受影响旅程 | 重建整个知识库、换Agent跑全套、扩大问法矩阵 |
| 同一业务期望两轮修复仍失败 | 停止第三轮同类补丁/采样；记录共同原因假设与一个能区分假设的检查。跨聊天/编号/模型批次累计计数，OS11继承原计数 | 继续改关键词、提示措辞或断言；靠换名字重新计数 |
| 有证据支持机制性改动 | 先说明旧机制为何失败、改动如何解释保存的失败输入，再固定一次受影响验证批次；仍失败则保留阻塞并转独立工作或提出具体决策 | 每次宣称“新机制”就无限重开验收，或重复相同请求当诊断 |
| 不影响当前主线的长尾 | 记一条带影响范围的缺口，排在本项之后或对应后续项；当前主线满足条件即可完成 | 追加为当前退出条件，或将旧失败改写为通过 |
| 越权、误写、来源撤回失效、虚假业务结果 | 阻塞所有受影响路径，先修真实边界；可继续不受影响的开发 | 降低守卫、伪造回执、在缺陷路径上宣布可用 |
| 环境、锁、供应商或账务未知 | 保留原失败/预留，不抢资源、不自动重发；等待或做独立实现，恢复后只补缺失检查 | 连续盲重试、把未知算零费用，或要求用户冻结所有开发 |

每次复跑都须能说清“验证哪个具体修改／未解决风险”。测试依赖、驱动、配置在运行前后绑定；相关漂移使该批失效，无关改动只做影响核对。只有文档变化、聊天换人、内部版本号变化，均不触发全套重测。

### 受阻时怎样继续

P0尚未收口时，先在本包内继续不依赖阻塞的实现；不得借独立阶段转序绕过用户“先补基础能力、再测后续”的要求。P0完成后，只有明确阻塞才按依赖拆开：D1的多意图问题不阻止D2的已定位知识解析缺口、D3已批准的内容发布服务、D4独立施工记录服务或D6语音适配开发；但这些阶段的完整Agent旅程仍依赖相应主线，不能提前关闭。D2的某个外部网页来源故障不阻止已有企业知识及真实项目服务的独立交付。D4的某条记录故障不应自动阻塞其他已独立验证的作品入口。D7供应商条件不阻塞D1–D6。

转序时在第2节注明未完成项、具体阻塞、独立工作及返回条件，并保持一次只集成一项。没有不受影响的工作时，报告期望/实际结果和所需决定，不能靠增加测试维持“持续开发”。

## 7. 怎样算最终交付

**D1–D6完成：装修Agent的软件主线可用。D7完成且所有PPT映射有实际证据：本计划覆盖的完整方案开发完成。生产上线另行授权。** 新计划不把旧未验范围变成通过，也不因文档换名抹掉旧失败。

最后只做一次按实际变更范围组织的综合收口，复用各项有效证据：

1. 同一测试客户从内容进入，图文/语音咨询、表达和更正需求、设计师接续，资料关联到项目。
2. 同一项目进入真实节点，师傅发记录、设计师核对问题、客户对具体版本决定，结果落实后回到原咨询，关注可取消，负责人可下钻协调。
3. D7具备真实条件时，设备开通、观看、故障与退场连到该项目，旧授权失效，费用和退款按真实回执呈现。

跨角色权限、来源撤回与恢复贯穿上述链路。若某项 `Limited`，只对已实现范围交付，说明阻塞范围及可用入口；不能用总测试通过数代替完整性。通用长尾、所有户型/材料/方言、供应商横向比较、性能极限矩阵另列优化事项，不是每个阶段的前置任务。

## 8. 后续开发只维护这些记录

- **本文：** 保持P0前置顺序、D1–D7范围及第2节唯一当前任务；P0实现时在原能力表更新实际复用入口、完成范围与阻塞。每次只更新相关证据指针、剩余问题、失败计数和下一项，不追加OS-*、AG-*、KB-*补丁队列或新的专项计划。
- **当前实现：** 路由、API、权限、状态变化同步[小程序清单](./miniprogram-system-modules.zh-CN.md)/[英文](./miniprogram-system-modules.md)和[后台清单](./admin-system-modules.zh-CN.md)/[英文](./admin-system-modules.md)的受影响记录。技术合同按需更新；原始日志和测试产物留在`tmp/`，计划只放简短结论及指针。
- **设计：** 修改视觉才更新原双语还原台账，不生成第二套设计权威；不要求每个失败/加载/文案变体单独出图或批准。
- **历史查证：** 一、二期合同及旧计划仅在需要某个接口、失败输入、费用或设计决定时定向查阅。旧“下一步”、停止通知、全套测试手册和自动接续聊天要求都不再调度开发；无须为了开始D1读完历史长文。
