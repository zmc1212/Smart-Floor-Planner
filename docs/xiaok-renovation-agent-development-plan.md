# 小K装修 Agent 开发计划（第一版）

> 2026-10-27建立，2026-10-31按用户明确的“像豆包一样自然交流、结合企业装修标准和自家工地阶段、四端自动收到日报与周报”重新校准。本文仍是小K开发的**唯一计划和任务入口**，第2节是唯一当前交付记录。
>
> **第一版：小K能自然解释企业标准、结合获权工地的真实阶段回答和主动提醒，并按日、按周自动生成及向业主、工人、设计师、老板投递各自的报告；点开后能继续追问。** 用户明确前期仅在小程序内投递，并提出四端都通过小K聊天接收，同时要求考虑多任务/多会话与同类产品。本计划推荐“自由咨询会话＋固定自动跟进会话＋每次独立报告”的组织方式，见3.4。自动日报、自动周报、站内未读和历史回看属于本版条件，微信订阅消息/短信移到后续，按需生成只是补充入口。原云工地直播、公开围观和设计师浏览保留在核心闭环之后。
>
> 本次修订取代此前“先做按需日报、定时推送不作为首版条件”的范围和旧“六项P0全部完成→D1–D7完整方案”的推进顺序。开发按“自然问答→一个水电工地的完整主动服务→扩展各阶段→原浏览能力收口”进行。旧实现、批准设计、失败次数、未知结果、费用与证据保留，第9节只用于查证。此次为计划修订，不提升实现状态；设备托管下单设计仍暂停，生产部署和真实客户外部消息启用仍守原授权边界。

## 1. 第一版交付什么

**用户不用懂工具或企业手册的目录：直接说需求，小K解释得明白、记得本轮条件、知道获权工地到了哪一步，并在该提醒和汇报的时候主动服务。** 四端指同一产品中业主、工人、设计师、老板四种角色的入口和权限视角，沿用一套Agent、一套知识服务和一套报告服务。

“豆包的效果”在本计划中落实为可验收的对话体验：自然表达、多轮追问、条件更正、多问项完整回应，以及清楚区分企业规定、一般解释、现场事实和未知项。采用成熟模型的理解与表达能力，不以逐字摘抄代替解释；不承诺与豆包全产品功能或所有问题逐项等同，也不把广泛竞品评测变成开发前置。

### 四端分别收到什么

| 角色 | 阶段提醒 | 日报 / 周报内容 | 可见边界 |
| --- | --- | --- | --- |
| 业主 | 本阶段要了解和确认的工艺标准、准备事项、验收关注点，用生活语言解释 | 本人项目当日/当周已发布进展、需要本人确认/准备的事项和下一步已确认安排；周报说明阶段变化与仍待解决的问题 | 仅本人获权项目、业主可见知识和明确发布的记录；不含工人内部草稿、内部讨论或其他客户资料 |
| 工人 | 当前项目/工种相关的施工做法、操作前核对和自检要点 | 获权施工记录、待补充/待核对事项、当前工艺要点；周报汇总本人相关未结事项和已确认后续工作 | 沿现有有效项目成员和原记录权限；共享现场对话不等于共享业主私聊，也不自动扩大商业信息权限 |
| 设计师 | 当前阶段的图纸、材料与工艺衔接检查，以及需要设计师核对的问题 | 获权项目当日/当周进展、待设计核对事项、已记录决定及对后续施工的影响 | 仅被分配/获权项目和允许查看的企业知识；不跨客户、项目或企业取资料 |
| 老板 | 获权工地的阶段风险、尚待核对的标准执行事项与需协调的问题 | 企业内获权工地的当日/当周进展、未处理事项、责任与协调线索；按工地区分并可下钻原记录 | 继承现有企业管理边界；admin/super_admin在所选企业继承负责人业务权限，不读取无授权的业主私聊 |

同一知识标准按角色解释，不复制成四个知识库。“提醒过”“看过”“记录了”均不等于施工达标、实际完成或工程验收。

### 一个工地的完整体验

业主自然询问水电问题并补充自家条件，小K依据企业有效标准解释；获权人员确认工地进入水电阶段，四端分别收到相关提醒；工人沿既有S04记录当天工作，有权人员核对并发布；到日/周触发时刻，系统自动生成、保存和投递各角色报告；用户点开问“这件事还需要我确认什么”，小K沿原项目、报告周期和有效来源继续回答。先在一个水电工地跑通这条链，再覆盖其他配置阶段；权限对照和老板汇总同时使用第二个合成工地。

### 第一版暂不扩展

设备租赁/托管下单、报价收费、押金退款、安装售后商业流程，完整设计方案审批/变更闭环，复杂经营分析，广泛图像识别/精确量测和语音能力扩展，均不作为第一版交付条件。已有功能和记录保留；若现有安全缺陷会影响第一版路径，仍须修复，不能以移出范围绕过。刚才拟做的D7业主下单设计不继续。

模型联网搜索、显式缓存、受控前缀续写和离线Batch不再全部作为本版统一前置；只保留第一版真实依赖的稳定对话、必要工具协议、知识检索、持久任务、权限、恢复和用量机制。不为首版重开框架或模型横向比较。

### 3.1 对话与自动服务的职责

| 部分 | 职责 | 本版实现原则 |
| --- | --- | --- |
| 对话Agent | 理解当前问题、追问与更正，调用获权读取工具并解释答案 | 普通解释允许有依据的自然转述；指定原文请求保留精确摘录。每个问项有回答或具体缺项说明；企业数值、条件及必须/建议等强度不得改写失真 |
| 企业知识服务 | 提供有效企业条款、适用阶段/工序/角色和可打开的原文 | 原有解析、发布、检索、Evidence及撤回机制继续负责；一般知识不能伪装成企业规定，无法解释的原因说明依据不足 |
| 工地业务服务 | 提供真实阶段、成员、记录、事项与已确认安排 | 服务端事实优先；用户聊天补充的条件保留来源，不自动写成正式进度或批准结果。正式写入仍经原授权/确认服务 |
| 自动报告流程 | 按阶段事件或日/周时钟取数、生成、校验并保存报告 | 时间、范围、接收人、去重和任务恢复由确定性代码负责；模型仅解释/总结获权输入，不决定是否到点、不猜收件人或施工事实 |
| 小程序内投递 | 将有效报告关联到收件人，提供摘要、未读、历史和继续问入口 | 原子保存投递记录，重进可见；生成成功、站内投递成功、用户已读分别记录。首版不接外部消息渠道 |

对话主链：**用户提问 → 当前身份/项目上下文 → 企业知识与必要事实 → 有依据的自然解释 → 来源/历史/追问**。

主动服务主链：**真实阶段事件或定时到期 → 按角色权限取事实与标准 → 生成并保存 → 按人站内投递 → 打开、重进与追问**。二者复用知识、事实与模型适配，自动流程无需让Agent自行规划每个固定步骤。这个划分采用[LangGraph工作流与Agent的职责说明](https://docs.langchain.com/oss/javascript/langgraph/workflows-agents)，保留当前运行时；这里只规定目标，不宣称已完成架构改造。

普通解释的完整性与真实性使用单独的语义验收，正式业务完成必须由真实服务回执证明。不得把逐字匹配作为所有自然解释的唯一判据，也不得删除数值、来源、承诺和权限守卫来换取通过。内部结构化协议应与用户可读正文分离；精确摘录不再作为所有共享工艺问答的目标答案形态。

#### 2026-11-04调整：前期知识问答与现场协作边界

**前期把工艺知识和现场协作分开处理。** 工艺做法、验收标准及注意事项，仅依据获权企业知识库或已启用的公开联网检索作答。企业标准保留适用条件和来源。公开检索提供一般装修知识，使用通用工艺问题检索，项目和人员信息留在原权限域。两类来源均缺少依据时，说明知识依据不足。

询问某个工地现在做到哪、下一步怎么排、周五能否施工、口头改动是否已确认，统一回复“这件事需要现场确认，请和现场团队核实。” 混合提问分别处理有来源的知识部分和现场协作部分。获权用户通过原报告卡片和详情查看现场原记录，报告绑定、收件人、读取权限和撤回沿原服务校验。回复继续通过既有会话保存和重进。

| 输入性质 | 回答时的职责与边界 |
| --- | --- |
| 已授权现场事实 | 通过原报告服务展示项目、房间/对象、时间截止、状态及原来源；现场协作追问使用统一话术 |
| 企业有效标准或公开知识 | 解释有来源的条款或做法，保留适用条件、原数值和必须/建议强度；公开知识按一般知识呈现 |
| 用户本轮更正 | 更新当前问题的指代与讨论条件，例如卧室改为客厅；不改历史原记录，不把改口当现场发布或批准 |
| 用户条件与期望 | “如果周五装灯”作为讨论目标保留；不自行补出确定日期、已确认排期或工期承诺 |
| 建议、未知与澄清 | 工艺知识以来源为依据，资料不足则明确说明；现场进度、施工决定和人员协调统一引导联系现场团队 |

1. **统一解释职责，收敛最终出口。** 普通解释与报告追问沿同一来源消费、引用和事实校验原则；报告正文沿确定性生成流程复用这些原则，其产物和投递生命周期继续独立。现有`report-native-final-v1`是受新run绑定的收尾实现，不因此为每个话题、角色、日期再造一种最终格式。发现旧分支冲突时，在原边界归一化或替换受影响分支；保留旧run恢复兼容，不在现有分支外再叠一套事实/引用/修复管线。
2. **内部格式不替代业务判断。** Q1/Q2等覆盖结构只帮助完整回应，不要求用户按固定句式提问，也不要求每句自然语言独立塞一条引用。引用应覆盖相应事实，必要的不确定说明和非量化建议可以不引用；原数字、来源和承诺校验仍保留。Schema能约束形状，不能证明引文支持房间、对象或施工结论。
3. **按问题类型判断合格。** 对客厅周五装灯或A户口头偏移，统一引导现场团队核实即可通过协作答复检查。可回答的工艺知识仍应依据实际来源解释。把用户条件写成已确认安排、把口头意向写成批准，或声称已经转交和通知团队，均不通过。
4. **用实际收益证明收敛。** 优先复用保存的失败输入，分别验证当前更正保留、原文范围、最终渠道和旧run兼容；模型调用数、schema/上下文开销、输入/输出分配及真实用量一起记录。不能只因新格式通过离线检查就再开语义批；也不能通过放宽权限、删除原失败或加未授权付费调用换成功。已有4次/72000等绑定按原合同保持，输出截断先查完整失败帧和分配，不盲目提高上限。

参考采用：[LangChain结构化输出](https://docs.langchain.com/oss/javascript/langchain/structured-output)用于生成/校验协议，[简单可组合流程的工程建议](https://www.anthropic.com/research/building-effective-agents)用于约束复杂度。这里是结合本项目失败记录作出的局部改造方向，不是上游已替本项目验证事实正确性或需要迁移框架的结论。

### 3.2 知识与现场记录的最小准备

- 继续使用微云1454和《精艺.pdf》。先核实水电所需条款的原文、适用条件、当前有效版本及四端受众；当前两页校对记录不等于所有阶段均已覆盖。后续按企业实际阶段逐项补齐，不能先发布其余28份草稿，也不要求重做正确的摄取链或先完成无关整本整理。
- 复用现有知识字段和运营入口维护阶段、细工序、受众、适用条件、页码/条款定位、有效版本与复核状态；确有缺字段时在原合同扩展。数值、单位、表格对应关系和印刷冲突要有原件依据，不凭模型补全。
- 工地继续使用企业真实阶段配置。防水等细工序要绑定实际记录/获权确认及阶段版本；没有细工序事实时只提供条件化关注点，不能声称现场已经开始或完成该工序。
- 现场事实来自既有S04自然语言/照片记录、核对发布、事项状态和已确认安排。日期、项目、作者、阶段/部位、完成/待处理内容、可见范围和来源版本必须可追溯；业主报告只取业主可见记录。报告不把知识建议变成已完成工作，也不把没有记录写成没有施工。
- 每个本版启用阶段都须有经复核的适用内容及一条实际提醒或报告旅程。开发验收可用带标记的合成参考和真实服务补齐有来源分支，同时验证资料缺项反馈。正式对客范围的真实企业资料缺口单独保留。覆盖状态沿现有知识运营及第2节证据维护，不再建立一份并行知识计划。

### 3.3 日报、周报和站内投递合同

- **周期：** 全部使用`Asia/Shanghai`。拟定可配置初值为日报每日20:00（当日00:00至本次截止时刻），周报周一08:00（上周一00:00至本周一00:00）。报告明确日期范围、数据截止时刻和生成时间；日报截止后的新记录进入补充版本或后续报告的补记，不冒充已覆盖完整自然日。修改时间只影响明确的后续任务，测试可以使用可控时钟。
- **启用：** 企业有权管理者配置适用项目/阶段、启停和时间；个人仅调整自己站内提醒偏好，不改变其他角色的订阅或事实可见性。默认针对启用且有效的在建项目；停工、完工、归档后的发送策略明确配置。执行时和打开时均重验当前关系；被移除成员不再接收或读取旧私有内容。
- **内容：** 日报包含当日实际记录、待本人处理、当前阶段工艺关注点、已确认下一步及缺项；周报汇总整周原记录、阶段变化、事项进展/遗留和已有依据的后续安排。待办负责人、期限和风险有记录才陈述；建议用明确建议语气。老板多项目汇总保留项目分组、分页/截断提示与下钻，不把有界读取包装成全部工地。
- **保存：** 持久保存项目/企业范围、周期、受众、事实截止、原记录与知识版本、生成状态及报告版本。同一范围/周期/受众的报告复用同一服务；重试核对原任务，事实更正生成可辨认的新版本，不静默修改旧报告。先按接收权限取数，不能先做全企业报告再仅靠前端隐藏私有段落。
- **幂等与恢复：** 定时任务按企业/范围/周期/计划时刻唯一占用，投递按报告版本/接收人唯一去重。Worker租约、重启补跑、并发领取和未知结果沿现有持久任务机制；补跑有界，不能集中重复刷屏。自动生成计入原用量/预算；额度或服务不足保留真实失败/待恢复状态，不生成假的成功报告。
- **站内到达：** 服务端自动生成和保存不依赖前台在线；关闭小程序期间形成个人未读记录，再打开时加载。应用内前台刷新可显示新摘要，不强制弹窗或抢走输入焦点。入口角标不代表已读，只有对应报告详情成功展示后确认阅读；同一身份不同入口共用已读状态，切换企业/身份清除旧缓存。
- **历史与追问：** 四端在小K聊天内共用按项目、日报/周报、日期筛选的简报记录与详情能力，服务端按身份裁剪。追问绑定reportId、项目、周期与有效来源，并说明报告截止后新变化；不把模型生成的旧报告再次当成独立事实来源。资料撤回/权限变化时重验并隐藏失效内容，保留可读状态说明。

### 3.4 多会话、主动投递与聊天内回看（2026-11-01设计/实施已批准）

**推荐：一个小K入口，保留多会话；自由咨询由用户新建，自动报告进入固定的私人跟进会话。后台每次独立运行并保存报告，前台不随每日报告新建会话，也不把日报插进用户当前任意话题。** 小K是统一助手，不等于只有一个无限增长的聊天上下文。初次存在有效服务关系且启用跟进时幂等建立对应跟进会话，以后复用；阶段变化不更换会话。

#### 四端如何组织会话

| 角色 | 默认自动跟进会话 | 多项目与专题处理 |
| --- | --- | --- |
| 业主 | 每个本人获权装修项目一条，如“XX小区·我家装修”；该项目阶段提醒、日报、周报进入同一会话 | 多套房分别跟进；普通选材/风格咨询可另开，除非用户明确选择，不把其变为自动投递目的地 |
| 工人 | 每个企业/当前身份一条“我的施工跟进”，日/周报按本人获权工地分组 | 同一周期以一张汇总卡展示多个项目，展开到项目报告；点击“问这份报告”锁定项目。工人沿`construction_staff`及项目职责，不混同量房员 |
| 设计师 | 每个企业/当前身份一条“我的项目跟进”，汇总获权项目中与本人有关的进展/待核对事项 | 项目分组与工人共用组件，内容按设计师权限；深入方案讨论可由用户另开带项目引用的专题 |
| 老板 | 每个所选企业一条“企业工地简报”，日/周总览附各工地明细 | 默认发汇总，避免每个工地各刷一条；下钻或追问某工地时绑定项目，跨项目查询须明确范围 |

四端得到不同受众投影，固定会话不等于群聊。一人多企业/多身份分别绑定；项目成员/职责调整后重新解析其可见项目。按人汇总卡只引用当前获权项目报告；不可访问的项目名、计数、摘要也不得泄漏。

**当前实现差距：** C01已有业主咨询及历史；`ConversationService.create`对admin目前走知识预览，S04 `SiteChatService`是每企业/项目唯一的`project_collaboration`共享会话。因此“员工/老板已有完整私人小K跟进窗口”尚不成立。V1-02须在原会话/参与者/消息/租户体系内补齐私人跟进类型与角色范围，复用同一Agent与聊天组件；不借用知识预览权限，不将个人报告写入共享S04，不把共享聊天私有化。原S04仍负责团队记录与协作。

#### 每次自动运行与用户看到的内容

1. 日/周任务到期，读取当前获权事实和企业标准，创建独立运行、报告与版本。模型上下文只取本周期/问题相关数据；不把几个月的聊天全文和旧模型日报反复回灌。
2. 解析确定的跟进会话绑定，提交一条幂等小K消息。消息携带reportId/版本、项目或汇总范围、周期与来源引用；自动报告消息不会再次触发普通答复或另一轮定时任务，避免自循环。
3. 聊天列表中该跟进会话显示真实未读和最新摘要；正在其他会话输入的用户仅见未读提示，不自动切换、滚到底部或清草稿。关闭小程序期间照常保存，下次打开看到未读，不产生手机外部通知。
4. 卡片展示日期/周期、项目/阶段、两三条重点及待本人处理，有“查看完整日报/周报”和“问这份报告”。长文在聊天内可滚动面板打开，返回保留位置；不把数千字正文连续塞满消息流。
5. 点击追问后，输入区标明正在讨论的报告/项目，问题沿该会话发送并绑定对应引用；直接打字只有在指代唯一时承接。多项目或多份报告指代不清时才简短确认，不默认取最后收到的其他项目。用户选择“另开专题”才新建讨论，并带最小获权来源引用。
6. 同一小K历史入口可区分“跟进/普通咨询”，跟进会话内提供“简报记录”，按项目、日/周、日期查找。历史索引与消息引用同一报告，不复制成第二份内容或另建底部Tab。工人/设计师/老板从原工作台/工地入口进入自己的小K会话，辅助入口只提示未读，不再形成独立报告首页。

#### 生命周期、打扰与权限

| 情况 | 处理规则 |
| --- | --- |
| 新建普通聊天、清空输入或改名 | 不改变定时投递绑定，不重复建跟进会话，不自动继承其他聊天的私有内容 |
| 多项目 / 阶段变化 | 同一跟进会话更新项目分组/阶段卡；需要新业主项目跟进时按唯一关系创建一次。已停用/无权范围不继续投递 |
| 未读 / 已读 | 会话消息未读与报告已阅分别有明确语义；真实展示/打开后更新对应状态，跨入口一致，刷新不重复插卡。已读不等于处理完成、同意方案或验收 |
| 无记录 / 失败 / 超额 | 区分本期暂无已记录进展、生成中、失败、待核对；保留有效阶段关注点和原任务恢复入口，不伪造成功或要求用户每日手点触发 |
| 更正 / 补记 / 撤回 | 新版本有明确提示，原报告不静默篡改；同版本不重复投递。来源/成员撤回使旧卡片摘要、详情和追问均即时受限 |
| 归档会话 / 停止提醒 / 删除 | 归档仅收起列表，明确提示“自动跟进仍开启，有新报告时重新显示”；停止提醒单独停用个人投递绑定，不影响其他用户。删除会话停用该绑定，不在次日静默重建；恢复须明确重新开启。原业务记录与报告按既有保留/删除合同处理 |
| 项目完工、停工、归档或退出 | 按项目生命周期和企业发送策略终止/暂停未来任务；已离开成员立即失去访问。不得用用户归档聊天代替项目状态变更 |
| 正在人工接待 | 保留报告任务和已生成结果，聊天插入/AI追问遵守原接待暂停合同，不自动恢复AI；聊天内获权历史仍可只读查看，积压不集中刷屏 |

#### 上下文与任务拆解的具体规则

1. **先保留关键输入，再压缩无关历史。** 每次请求先固定当前身份/企业/项目、当前用户原话及更正、尚需回应的问项和明确报告引用；相关Evidence、近轮与必要早期原话按既有预算装入。标准、用户条件、现场事实、模型建议和未知保持来源区别；检索内容/历史里的指令不能升级为system或当前授权。
2. **原文与摘要各守职责。** 不裁掉否定、条件、单位、先后关系及来源定位来凑长度；旧预算/房间用途被更正后不得由摘要恢复。摘要只帮助定位和续聊，不成为企业规定、现场进度、未处理状态或正式业务结果。较早原文沿原服务检索，日/周报仍取原记录，不能反复总结旧模型报告作为新事实。
3. **引用必须可重读且可撤销。** 被卸载/召回的数据继续绑定原企业、主体、会话/项目、来源版本/hash及适用epoch；重读、恢复、展示和追问均经原source resolver授权。撤回、成员移除或来源变化后，预览、摘要和缓存不得绕过失效；无法取回时报告具体缺项，不补造内容。仅减少模型输入不代表checkpoint或数据库字节已减少，分别测量。
4. **预算与恢复不另起账。** 包括system、工具schema、正文、图片、输出与下一工具结果的空间，沿`agentRequestBudget`及原调用/用量预占；不把上游85%或20,000 token等默认值当本项目阈值，不为普通问答新增规划/摘要调用。持久checkpoint保留原始配对与真实回执，只改变给模型的获权投影；压缩/重读失败不无限重试、不自动换模型。输入字节/估算token、选中及省略的来源ID、调用数/耗时与实际用量沿现有观测记录，日志不复制私有正文。
5. **清单用于完整回应，不用于宣告业务完成。** 多问项分别得到有依据的解释、必要澄清、具体无依据项或真实受阻项；追问和改口只更新受影响条件/问项，不丢其余问题。复用原coverage/来源及最终回答校验，不能新增一串逐字/关键词守卫，或让模型的`completed`代替服务写入。自然转述与企业数值/条件/承诺真实性仍分别检查；本节不是绕过V1-01停测边界的新机制批授权。

#### 主动服务的具体规则

1. **一次到期、一份范围、一次独立运行。** 时区和日/周窗口沿3.3；阶段事件沿真实阶段版本/outbox。服务端确定任务身份、计划时刻、事实截止、受众及有效设置/绑定版本，沿原schema保存必要快照。模型只接收本周期获权输入，不继承另一私聊或无限增长的跟进历史，不判断是否到期或选择收件人。先核查已有字段/约束，缺什么补什么，不预先新建一套调度存储。
2. **固定目的地不依赖“最近聊天”。** 幂等解析原私人跟进绑定，企业/主体/角色/项目范围和绑定版本参与校验；不得复制OpenClaw单用户共享DM的默认值到多租户四端。新普通咨询、改名和页面切换不改变投递目标。调度后至投递前发生停用、删除、退出、改绑或人工接待时，按3.4停止/撤销/暂存，旧Worker不得将结果写入新的无关目标。自动报告标明系统来源，不能再触发普通Agent回复、重新调度或消息自循环。
3. **生成与投递分别恢复。** 已保存且仍有效的报告投递失败时，只重试同版本投递，不重跑模型生成；有效性变化则保留原结果并按原合同撤销/建立可辨新版本。沿原事务、唯一约束、租约/CAS及outbox维护逻辑单次可见。租约过期的旧Worker不能覆盖新状态；丢回执先查原run/报告/消息/投递记录。明确尚未执行的失败才按有界策略恢复；可能已产生结果或费用的unknown保持未知，不因超时、重启、改标签或换聊天重派。
4. **补跑有界，必需报告不被静默吞掉。** 断线/重启后核对到期任务、已完成版本及当前授权，限制每tick补跑数量、并发和积压投递，明确哪些周期待补/跳过及原因，不把缺失历史写成已送达。普通阶段/工序提醒只在有效变化或需行动时发送，同事件去重；明确启用的日报/周报即使无新记录也须保存真实“本期无已记录进展/缺项”结果。静默/聚合只抑制重复打扰，不抹掉任务失败、撤权或必需周期报告；人工接待积压沿3.4处理。
5. **状态与证据保持可区分。** 事实就绪不等于自然语言报告完成，生成成功不等于已投递，已投递不等于已阅，已阅不等于待办完成或施工合格。状态名称映射现有合同；持久保留任务/报告版本/消息/接收人与回执关联、错误原因及恢复动作。失败或无记录沿批准的共用状态表达，新增视觉仍先确认设计。

### V1-02：一个水电工地的四端主动服务完整可用

按第3节实施阶段事件与日/周任务，持久保存报告、版本、消息和个人阅读状态；自动生成不要求用户先提问或保持页面打开。报告只引用获权记录与有效企业标准。共用聊天卡片/详情/追问与历史索引；新建普通咨询不改变固定投递目的地，定时执行不每天创建新会话。

**固定旅程：**

1. 水电阶段变更及真实现场记录/发布后，四端分别在小K看到对应提醒；用可控时钟及跨日/周合成记录触发真实调度、Worker、报告保存和消息投递，日/周各有结果。至少一轮生成时客户端关闭，之后原生重进查看未读、卡片、完整报告、原记录和知识出处，并输入自然追问；老板区分两个工地，员工按项目分组，业主看不到内部记录。模拟时间不等于模拟报告/回执，不等待自然一周，也不用手点生成代替调度。
2. 保留无记录、补发/更正、阶段纠正、重复/并发事件、生成/投递失败、丢回执、Worker重启、成员移除和资料撤回检查。另覆盖正在另一会话输入、多身份切换、聊天从未打开、跟进停止/删除与普通会话新建，证明不串会话、不重复、不自循环、不遗留私有摘要。报告追问涉及项目歧义时正确澄清，阅读不会自动完成待办或批准施工。

### V1-04：同一云工地直播支持本人查看和公开围观，并能看设计师

**交付：** 云工地是一项直播能力。业主按本人项目权限进入；对明确允许公开围观的工地，访客通过围观入口观看同一工地获准公开的直播画面。复用现有设备、流媒体与播放基础，不再单列“公开直播产品”或要求先实现设备商业托管。已有可用回放保留，不新增一套录像存储/计费服务作为首版前提。

围观沿现有公开工地合同完成必要授权与审核，明确可公开的摄像头/画面；未允许公开的设备、私有记录和业主私聊不随工地公开。成员撤权和取消公开分别使相应旧入口/会话/媒体失效。无设备、设备离线、直播失败如实呈现并可恢复，不能用成功提示或照片代替直播。

设计师沿既有公开主页和作品浏览入口，内容撤回即时受限，能返回小K继续咨询；不扩展为新的接待、预约或分佣系统。

**固定旅程：**

1. 同一实际可用测试工地：业主打开本人直播，访客在未公开时不可看；获权人员批准该工地围观后，访客实际播放公开允许的直播。移除成员、关闭围观及重进分别验证对应旧授权失效；覆盖离线/断流与恢复。
2. 查看已公开设计师和作品，进入/返回小K保持上下文，撤回作品后旧入口受限；不创建重复客户或改变来源归属。

真实视频源和必要公开授权缺失时，明确缺少什么、影响哪条路径；其他三项继续开发，但第一版云工地能力不能标为完成。设备采购、外部服务购买和生产启用仍须原有授权。

## 5. 实施边界

1. **一套Agent、一套企业知识库服务。** 复用当前LangChain/LangGraph、模型适配、工具协议、持久任务、幂等、用量与恢复。扩展前只核对相关维护中实现、测试和供应商已知问题；有具体缺口才改，不重写平台。
2. **标准与事实分开。** 企业标准来自有效知识，项目进度/施工记录来自原服务；不能因符合标准措辞就判定现场合格，也不把直播画面自动送模型做工程质量结论。正式v4墙图只读消费，不写回旧layout副本。
3. **四端按身份与项目授权裁剪。** 企业、知识受众、本人项目、有效成员、公开围观各守原边界；公开工地不意味着公开聊天、日报或其他摄像头。管理者继承和明确所选企业的规则不变。
4. **提醒与日/周报自动运行、仅站内投递。** 复用outbox/Worker、原会话/参与者与用量机制；先按权限取数，再向固定私人跟进会话投递。前台离线不阻止后台生成；生成、投递、已阅各有真实状态。微信订阅、短信、邮件和外部渠道购买不属于本版验收，也不作为开发阻塞。
5. **设计沿已有批准源。** [双语还原台账](./miniprogram-design-restoration-ledger.zh-CN.md)/[英文](./miniprogram-design-restoration-ledger.md)与现有组件为基准。按3.4补齐共用会话组织、报告卡片/详情和追问状态，取得新增视觉/交互的明确实施批准；普通状态与日/周/角色文案复用组件，不为每种文案画一页。下单设计暂停不阻塞既有知识服务，尚未批准的新增界面不影响独立后端工作。
6. **测试、费用与部署权限保持。** 只用授权开发/隔离库和明确标记的合成数据；不污染生产。原生沿Stable DevTools、官方SDK、单控制器、原锁与窗口核验，不用Computer Use、不抢资源。模型调用不新增预算，unknown和历史费用保留；生产上线单独授权。

## 6. 验收与失败处理

### 6.1 正常开发持续推进，同一问题的重复试修止损（2026-11-03最新用户决定）

用户明确答复：**“正常开发继续，仅重复试修止损”。** 此决定覆盖本计划此前把“同一业务目标最多两个工程包”作为整体停工上限的规则。工程包、原失败、漂移和费用计数保留为历史证据，不再阻止正常开发、已定位缺陷修复、相关测试、文档及本地提交；不要求用户重复批准继续开发。不得通过改变名称删除失败、放宽权限或把不完整旅程写成完成。

1. **开工绑定用户动作和实际缺口。** 在第2节维护同一个当前交付记录，说明入口、预期结果、已观察I/O、因果依据、必要改动、有限完成检查、证据复用及下一动作。普通确定性修复直接推进，不为每个补丁新建阶段、预算或批准门禁。
2. **只停止当前批或相同问题的反复试修。** 固定批遇首个失败或unknown即停止继续派发，随后自动保存证据、按原始trace归因并执行能独立推进的下一动作。同一业务期望连续两轮修复/复验仍失败时，停止同类提示词、正则、封套或重采变体，先提出共享原因和可区分检查。有证据的机制修正按原授权推进；不能只更换措辞或采到通过。批次结束和局部提交均不构成整体停工条件。
3. **检查必须返回用户链路。** 修复后立即验证受影响的正常入口、真实写入/读回、反馈、重进、权限及恢复；通过才完成该部分。仍受阻时，继续不依赖该问题的已授权开发；如果所有剩余路径确实共用外部阻塞，报告具体缺失条件，不能停在提交、测试数或文档检查点。
4. **保留原生和付费调用的证据边界。** 原native01–06、报告首稿失败、unknown和历史成本不删除或重算。先修已证明依赖并离线隔离变因，再固定恢复范围；不因本次决定自动重放unknown、扩大模型/图片调用或重跑全产品。确定性代码/路由/包体修复不需要新增模型调用。
5. **按实际依赖验证，不无限扩测。** 快速受影响检查、真实服务/兼容和必要Stable原生验收顺序推进。新实质语义核心仍按原固定两次配置模型试验；普通确定性变化不追加无关模型案例。复用有效未变证据，保留每个首失败。
6. **绑定源码、配置与运行资源。** 派发前后保存实际依赖；批内漂移原样标无效，先查影响再执行必要范围，不事后缩小绑定。后续无关改变做影响核对，不自动回放全套。只使用自有隔离库/端口/Worker/媒体和串行Stable控制器，清理由finally负责，不抢他人资源或要求例行冻结。
7. **继续开发不等于放宽产品边界。** 租户、来源/身份撤回、原咨询归属、幂等、真实回执、用量、批准设计、原生限制及生产部署权限保持。容量接续仍按第8节，继承失败/成本/资源，不因新聊天重置。

## 7. 第一版怎样算完成

以下同时成立才交付第一版，不能用总测试数量或后台内部进度代替：

1. 业主能从实际小程序入口向小K自然问装修知识，围绕本企业有效资料得到有依据的回答并连续追问，出处/历史可重进，缺资料与失败能正确恢复；其余三端的相关提问守住原权限。
2. 同一工地真实节点变化后，业主、工人、设计师、老板分别收到适用于自己的企业工艺标准提醒，能继续追问，重试不重复，撤权/撤回后停止相关访问与投递。
3. 用户不发消息、客户端关闭时，四端日报与周报仍按配置自动生成并持久投递到各自小K跟进会话；未读、完整内容、历史、原记录和继续追问可用。老板能区分至少两个工地，员工报告按获权项目分组；普通咨询与自动跟进并存，不每份报告新建窗口、不串入其他话题。记录、待办、建议和未知项准确，预算/失败/恢复状态真实。
4. **同一云工地直播能力**支持业主本人查看与获准公开后的访客围观，真实视频播放、重进、关闭公开/成员撤权和失败恢复有证据；设计师资料/作品可浏览并回到小K。
