# Admin System: Current Module Inventory

This is the current Admin runtime inventory. It records stable entry points,
contracts, permissions, and limitations only. Implementation history belongs in
Git commits; do not append dated change logs here.

## Shared architecture

- Next.js 16 App Router, React 19, Tailwind CSS 4, Ant Design 5, and Ant Design Pro.
  Root layout mounts a client `AntdReact19Patch` that imports
  `@ant-design/v5-patch-for-react-19` so Ant Design 5 wave effects and static
  methods work on React 19.
- PostgreSQL 17 with `drizzle-orm`/`pg` is the deployed runtime. Tenant-aware
  reads and writes use repositories, transactions, and RLS.
- Admin sessions use cookie/JWT authentication. Platform and enterprise roles
  are enforced by route guards and menu permissions.
- External provider and object-storage I/O runs outside short database
  transactions. API handlers serialize `bigint` values through DTOs.
- Formal floor plans are version-4 surveying graphs. Viewers, DXF, 3D, and AI
  consume derived read models and never write legacy layout fields.

## Status legend

`Implemented` means a real page/API/data path exists. `Limited` means a defined
role, provider, source shape, or operational condition restricts it.
`Placeholder` means UI or a mock path exists without the promised persistence or
integration.

## Module inventory

Professional endorsements are an implemented tenant-scoped staff capability. Enterprise and platform administrators use `GET/PUT /api/professional-profile-settings` from `/staff` to set designer/measurer default titles, default experience years, a service threshold of at least 100, forced enterprise content, and `follow_staff` / `force_show` / `force_hide` title visibility. They use `GET/PATCH /api/staff/[id]/professional-profile` for a staff-specific title override, career year, title preference, profile lock, and exact-count opt-in. Designers and measurers use `GET/PATCH /api/miniprogram/staff/professional-profile` for unlocked self-service fields. Customer DTOs receive only the resolved `professionalProfile`; raw counts remain internal. Designer counts are distinct leads with a customer-visible publication credited to the designer at publish time; measurer counts are distinct leads with a completed formal v4 floor plan owned by the measurer. Counts at or below the enterprise threshold never leave internal/Admin responses, and exact display is available only above that threshold. These fields do not change assignment eligibility.

Service-address completion is part of the appointment service fact. `measurement_appointments` stores the manual service address plus optional `location_name`, bounded GCJ-02 latitude/longitude, and coordinate system. Appointment and lead DTOs rewrite PostgreSQL `tstzrange` text (`2026-08-23 01:00:00+00`) to ISO-8601 (`2026-08-23T01:00:00.000Z`) so Mini Program `Date` parsing can place visits on the Asia/Shanghai calendar day. `GET /api/appointments/availability` omits past starts and, when the lead already has a confirmed appointment, excludes that row so same-day reschedule can pick an overlapping replacement; other leads still treat the measurer as busy. `POST /api/appointments` and `POST /api/appointments/[id]/address` accept that optional map location; address updates remain versioned and write previous/new location snapshots to the `address_updated` audit event. Mini Program callers are resolved as staff first (`staff._id` vs assigned designer/measurer); Admin cookie JWT remains the fallback. The Admin lead drawer and Mini Program appointment detail use the same entry. Creating or updating a service address copies an empty lead `communityName` in the same transaction from the map `locationName` when present, otherwise the typed address (trimmed to 160 characters; no overwrite). Mini Program appointment detail still offers staff an explicit sync for historical empty communities. `POST /api/appointments/[id]/complete` additionally requires a linked completed formal v4 survey floor plan with at least one closed space and returns `appointment_survey_required` (409) otherwise. Editor submit only stores the formal plan; lead `designing`, designer survey-completed notify, and slot release happen only after appointment-detail confirm-complete.

## Formal surveying boundary

The authoritative contract is
[`surveying-module/formal-surveying.md`](./surveying-module/formal-surveying.md).
`FloorPlan.layoutData` contains only `version: 4`,
`measurementMode: 'surveying'`, and `surveyGraph`. Measurements are immutable
audits; dimensions and room summaries are derived read models. `/floorplans/[id]`
renders the 2D plan with the Mini Program `surveyCanvasRenderer` mirrored into
`admin/src/lib/survey-runtime/` and does not write the graph. Completed formal
v4 saves persist a PNG snapshot of that canvas on `floor_plans.preview_asset_id`
and never into `layoutData`. DXF still uses
`admin/src/lib/surveyWallSolidPlan.js`, which uses the same local convex/concave
join rules as the Mini Program planner.
DXF generation is likewise read-only: `admin/src/lib/dxf.ts` adapts the graph
to the MIT-licensed writer, emits unioned inner/outer wall `LINE` faces after
opening gaps, inserts hinged-door blocks with an open 90° thick leaf, gray dashed
arc, and jamb rectangles, writes sliding-door double rails and four inset window
lines away from the wall faces, labels closed rooms with four-line MTEXT, wraps the drawing in a
full-height model-space title panel and yellow north arrow filled from the
linked customer lead (enterprise name and assigned designer), and rejects drafts, invalid v4 data, and plans
without a closed space before emitting a download.

## Commission boundary

The measurer-designer acquisition contract is retired and retained only as a
