### 3.2 启动与隔离规则

1. 开始前读根 `AGENTS.md`、最近指令、适用模块清单及本计划；涉及远端访问先读远端开发双语合同。先检查已有worktree、分支及实际依赖，不能把旧worktree视为可占用资源。

3. worktree不会复制脏改动。本计划文件本身也可能尚未提交；新聊天应先从原工作区读取本文件。对确需的未提交依赖记录路径/hash并保留精确快照或补丁，不能漏掉依赖、丢弃原修改、复制凭据，或为准备worktree提交无关改动。
4. 第一波优先离线类型检查与本地资料处理，不需要新增服务。若后续并发运行服务，必须独立数据库、端口、Worker、配置、夹具/媒体、输出和provider记录；准备不足时只做离线工作，将真实服务检查交由主线串行执行。无需先搭建CI或容器平台。
5. 每线使用自己的 `tmp/parallel-support/<lane>/<delivery>/` 保存运行证据，交付时给出绝对路径、提交和依赖指纹；该目录位于其真实worktree，不共写一个清单。敏感数据不入Git。可复用工具进代码，当前结论回写本计划，避免新增平行总结文档。
6. Stable DevTools原生验收保持同一真实项目、既有锁、idle-queue和单控制器串行纪律。辅助线不创建临时小程序项目或占用原生窗口；第一波无新增原生验收需求。
7. worktree不能隔离CPU、内存、磁盘和共享工具服务。辅助工程线同一时刻只运行一个重型检查；资料先逐页或小批量处理。主线正在构建或执行原生验收时，辅助线优先做轻量分析，不同时发起大批渲染、OCR、Embedding或全套构建，也不抢占或终止主线任务。

本计划不要求迁移或重建两条正在工作的主线环境，不引入全局冻结、例行人工验收或跨聊天发消息的前置。可以只读查阅主线记录及本地成果；发送消息给其他聊天仍须有直接授权。

## 4. 工程线 E-01

### 4.1 目标与首批范围

用户结果：两条主线在完整构建时，不再被同一个已确认的测试夹具状态类型问题阻断。

先读[夹具脚本](../admin/scripts/xiaok-manual-fixture.ts)的状态初始化、持久清单、`key`/`once`/`write`及重进处理。捕获实际配置下的原诊断，再围绕同一持久状态结构进行最小类型修复。保留原操作键、输入、成功回执、未完成记录和重进语义。

启动时若原负责人已经修复且有当前版本的有效证据，直接复用并回填采用情况，不再提交另一种修法。下一项只从新的已证实共同阻断选择。

首批不整治全库历史诊断，不修改业务实现、权限、Agent提示词、最终回答守卫或任何unknown处理。修复以明确类型及必要的真实边界验证为准，不用 `any`、`@ts-ignore` 或强转掩盖未验证输入。

### 4.2 复用与检查

- 复用实际npm脚本、既有类型检查方式和ESLint；先做受影响静态检查，再在有完整依赖的稳定worktree执行必要构建。`npm run build` 的prebuild含受支持的缓存治理与量房同步，要记录其输出和文件变化，不绕过或改写主线缓存规则。

## 8. 提效衡量与收敛
