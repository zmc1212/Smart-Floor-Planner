# Smart-Floor-Planner 后端代码审查报告

> 审查日期：2026-09-12。本报告由只读代码审查产出（会话任务「分析下目前后端的代码逻辑 有没有明显bug」的继续执行结果），未修改任何代码。
> 审查范围：`admin/src`（lib 核心逻辑、db 层、289 个 route.ts 抽查、proxy.ts）。所有行号均已核实。

## 高危（实锤，附证据）

### H1. 中间件 Bearer 头无条件放行 + 多个路由完全无鉴权 = 未登录接管后台
- **位置 1（放行链）**：`admin\src\proxy.ts:137-148`

  ```ts
  if (
    pathname === '/api/health' || ... ||
    authHeader?.startsWith('Bearer ')
  ) {
    return passThrough(request);   // 不做任何 token 校验
  }
  ```
  任何请求只要带 `Authorization: Bearer 任意字符串` 即跳过全部中间件鉴权，直接进入 route handler。
- **位置 2（无鉴权 handler）**：以下路由文件内没有任何鉴权调用（逐文件 grep 确认，既无 cookie/Bearer 校验，也无 withTenantRoute/getSessionUser）：
  - `admin\src\app\api\admin-users\route.ts:40（GET 列出全部管理员）、67（POST 创建管理员，允许 role='super_admin'）` — 全文仅 `withPlatformTransaction`，无任何身份判断
  - `admin\src\app\api\admin-users\[id]\route.ts:21（PATCH 可改 role/重置 newPassword）、148（DELETE 删除管理员）`
  - `admin\src\app\api\users\route.ts:8（GET 全量用户 PII）、53（POST 创建用户，passwordHash 直接取自 body）`
  - `admin\src\app\api\ai\image-proxy\route.ts:3（GET 服务端 fetch 任意 url）`
  - `admin\src\app\api\save-icons\route.ts:6（GET 内用 exec('node -v') 泄露服务器信息）`
  - `admin\src\app\api\devices\verify\route.ts:7（POST 返回设备码是否命中）`
- **触发场景**：`curl -H "Authorization: Bearer x" -X POST /api/admin-users -d '{"username":"pwn","password":"123456","phone":"13800000000","role":"super_admin"}'` → 直接创建超级管理员；随后 PATCH `/api/admin-users/[id]` 可重置任意管理员密码。无需任何有效凭据。
- **修复方向**：删除 proxy.ts:145 的 `authHeader?.startsWith('Bearer ')` 兜底（改为仅对 `/api/miniprogram/**` 放行）；给 admin-users/users/image-proxy/save-icons/devices-verify 补上 handler 级鉴权（`withTenantRoute` + 角色白名单），并把 `/api/admin-users`、`/api/users` 加入 `ROUTE_PERMISSIONS` 的 `admins`/`users` 权限映射（见 H2）。

### H2. 权限映射缺口：任意低权限登录用户可创建/篡改/删除 super_admin（不依赖 H1 的 Bearer 技巧）
- **位置**：`admin\src\proxy.ts:182-186` 权限回退逻辑：

  ```ts
  const requiredPermission = ROUTE_PERMISSIONS[pathname] ||
    Object.entries(ROUTE_PERMISSIONS).filter(([route]) => ... pathname.startsWith(route))... ||
    ROUTE_PERMISSIONS['/'];   // = 'dashboard'
  ```
  `/api/admin-users` 在 `ROUTE_PERMISSIONS` 中无精确键也无前缀键，回退为 `dashboard`；而 `admin\src\lib\admin-user-roles.ts:121-175` 中**所有角色**（designer/salesperson/measurer/viewer/enterprise_admin）默认权限都含 `dashboard`。handler 又零校验（见 H1 位置 2）。
- **触发场景**：任一刚入职的 `measurer` 登录后台（拿到合法 cookie）后，POST `/api/admin-users` 创建 `super_admin`，或 PATCH 重置平台管理员密码，完成垂直越权。
- **修复方向**：同 H1 第二条；并让 admin-users 类 handler 自行校验 `context.role === 'super_admin' | 'admin'`（当前代码库其他路由如 `api/staff/route.ts:255-263` 已有此模式，可复用）。

### H3. 未鉴权 SSRF 代理
- **位置**：`admin\src\app\api\ai\image-proxy\route.ts:3-31`

  ```ts
  const targetUrl = searchParams.get('url');
  const parsed = new URL(targetUrl);
  if (!['http:', 'https:'].includes(parsed.protocol)) ...
  const response = await fetch(targetUrl);   // 无内网/localhost 黑名单
  ... return new NextResponse(buffer, ...)
  ```
  该文件无任何鉴权；叠加 proxy.ts:145 Bearer 放行，未登录攻击者可让服务器请求任意 URL 并把响应体原样带回（云元数据 169.254.169.254、内网 Postgres 端口、localhost 等）。
- **触发场景**：`curl -H "Authorization: Bearer x" ".../api/ai/image-proxy?url=http://169.254.169.254/latest/meta-data/"`
- **修复方向**：删除该路由或加鉴权 + 解析目标 IP 并拒绝私网/环回/链路本地地址段；限制响应大小与 content-type。

## 中危

### M1. JWT 回退密钥硬编码（6 处）
- **位置**：`admin\src\lib\auth.ts:30`、`admin\src\lib\session.ts:38`、`admin\src\lib\admin-session.ts:13`、`admin\src\lib\miniprogram-jwt.ts:3`、`admin\src\proxy.ts:97` 均为 `process.env.JWT_SECRET || 'fallback_secret_random_123'`；`admin\src\lib\crypto.ts:3` 另有 `DEFAULT_SECRET = 'smart-floor-planner-pollinations-secret'`（AES 密钥来源，`crypto.ts:8` 兜底链最终也落到它）。
- **触发场景**：生产环境漏配 `JWT_SECRET` 时，任何人可用公开源码中的字符串自签 admin token，直接通过 `getTenantContext`/`getSessionUser` 全部校验。`crypto.ts` 的媒体存储密钥在非生产环境同样落到默认值。
- **修复方向**：生产环境启动时检测 `JWT_SECRET` 缺失即拒绝启动（参考 `crypto.ts:61-64` 对 `MEDIA_STORAGE_KEY_ENCRYPTION_SECRET` 已有的做法）。

### M2. 登录接口无限流/无锁定
- **位置**：`admin\src\app\api\auth\login\route.ts`（全文 120 行，无任何尝试计数/延迟/验证码）；`admin\src\lib\admin-credential-auth.ts:12-30` 逐候选者 bcrypt 比对。
- **触发场景**：对 `username+password` 做在线爆破；由于 `authenticateAdminCredential` 支持手机号登录，还可先通过任意泄露手机号的接口（如 `/api/users` H1）撞库。
- **修复方向**：按 IP+账号维度限流与失败锁定；中间件层全局 429 兜底。

### M3. 停用/降权账号的令牌在 24h 内仍完全有效
- **位置**：`admin\src\lib\auth.ts:13-59`（`getTenantContext` 只验 JWT 签名，不查库）；`admin\src\lib\tenant-route.ts:45-62`（`withTenantRoute` 只校验角色枚举与企业状态，不校验 `admin.status === 'active'`）。对比 `admin\src\lib\session.ts:41-57`（页面 session 会回库查 `admin.status !== 'active'`）。JWT 有效期 24h（`admin\src\lib\admin-session.ts:5`）。
- **触发场景**：管理员把违规员工 `status` 置为 `disabled` 后，该员工已持有的 auth_token 在最长 24h 内仍可调用全部 API（H1 修复后仍是如此，只是危害面缩小）。
- **修复方向**：在 `withTenantRoute` 内复用 session.ts 的回库校验（可用短 TTL 的进程内缓存控制 DB 压力），或缩短令牌有效期 + 引入刷新令牌。

### M4. 佣金 mark-paid 管理端与小程序端校验不一致（零金额放行）
- **位置**：`admin\src\app\api\lead-commissions\mark-paid\route.ts:26`（admin 端调用 `repository.markPaid(enterpriseId, commissionIds, actorId)`，无 options）vs `admin\src\app\api\miniprogram\enterprise-commissions\mark-paid\route.ts:31`（小程序端传 `{ rejectZeroAmount: true }`）；`admin\src\db\repositories\lead-commission-repository.ts:518-520` 中 `rejectZeroAmount` 才会拦截 `payableAmount = 0` 的提成。
- **触发场景**：企业负责人走小程序端会被拦截"零金额提成需先录入实际付款金额"，但同一企业管理员走管理端可直接把 0 元提成标为已支付，台账金额与实际打款不一致。
- **修复方向**：两端统一传 `rejectZeroAmount: true`，或管理端也强制要求 `payments` 带 `paidAmount`。

## 低危/待确认

### L1. cookie 解析正则可被子串匹配
- **位置**：`admin\src\lib\auth.ts:17` `cookie?.match(/auth_token=([^;]+)/)` — 名为 `x_auth_token=`、`fake_auth_token=` 的其他 cookie 也会命中。攻击者需能设置受害者 cookie（如子域 Cookie Tossing），故列为低危。修复：`/(?:^|;\s*)auth_token=([^;]+)/`。proxy.ts:95 用 `cookies.get` 无此问题。

### L2. 员工量房数据写入的应用层越权由 RLS 兜底（待确认部署）
- **位置**：`admin\src\app\api\floorplans\route.ts:168-181` 中 `leadRepository.findById(leadId)`（见 `admin\src\db\repositories\lead-repository.ts:449-457`，不带 enterpriseId 过滤）+ `canStaffMutateLeadSurvey`（`admin\src\lib\lead-staff-access.ts:10-19`，enterprise_admin 对任意企业的 lead 一律返回 true），应用层未做跨企业校验。实测确认 `admin\drizzle\0001_easy_bruce_banner.sql:1133-1156` 对 `lead_floor_plans` 有 `FORCE ROW LEVEL SECURITY`，且 `docker-compose.yml:20` 应用以 `sfp_app` 角色连接，跨企业写入会被 RLS 拒绝。**待确认**：生产 DATABASE_URL 是否同样使用 `sfp_app`（若使用 owner 角色，RLS 不生效，该路径升级为跨企业写入）。
- **修复方向**：应用层补 `lead.enterpriseId === context.enterpriseId` 校验，不依赖数据库兜底。

### L3. 设备校验接口可枚举设备码
- **位置**：`admin\src\app\api\devices\verify\route.ts:7-21` — 每次请求拉全量设备表做 `reportedId.includes(code)` 子串匹配，无频率限制；叠加 Bearer 放行（proxy.ts:145）可被未登录暴力猜测设备码。修复：改为精确等值查询 + 限流 + 鉴权。

### L4. CRON 密钥非常量时间比较
- **位置**：`admin\src\app\api\internal\lead-claim-windows\run\route.ts:8` 用 `===` 比较 `x-cron-secret`；同目录 `lead-assignments/[leadId]/retry/route.ts:12` 已正确使用 `crypto.timingSafeEqual`，前者应保持一致。理论性风险。

## 检查过且干净的部分（简述）

- **佣金/支付金额**：全链路用整数分单位（`lead-commission-repository.ts:82-105` `parseDecimal/formatDecimal/roundHalfUp`），`markPaid`/`confirmPayments`（500-598 行）`SELECT ... FOR UPDATE` + 状态条件更新 + 幂等去重，无 float 计钱；schema 中无 `doublePrecision` 金额列（17 处 numeric）。AI 点数账户 `ai-credit-repository.ts:74-103` 为原子条件 SQL 更新 + `operationId` 幂等台账。
- **预约状态机**：`appointment-repository.ts` 创建/改期用 lead 行锁串行化 check-then-act（421、710 行），乐观版本号（741-753 行），`expireAppointmentRow` 带版本条件更新与 SAVEPOINT 容错（186-198 行），量房顾问冲突用 `tstzrange &&` 重叠检测（242 行）；时区换算 `appointment-scheduling.ts:76-105` 用双遍偏移法正确处理 DST。
- **会话受众隔离**：admin token 拒绝 `aud=miniprogram`（`auth.ts:34-36`），miniprogram token 强制 `aud=miniprogram`（`miniprogram-jwt.ts:39-41`），且小程序上下文每请求回库校验 `contextVersion`（`miniprogram-auth.ts:76-79`），防降权后继续使用旧 token。
- **事务与连接**：`db/transaction.ts:36-54` finally 中 `client.release()`，异常时 rollback；连接池有 statement/idle 超时配置。未发现连接/流泄漏。
- **破坏性操作**：企业清空需 `ALLOW_TENANT_ENTERPRISE_RESET=true` + 全名确认（`enterprise-purge/route.ts:16-48`）；内部种子/CRON 接口均验密钥，seed 强制 ≥32 字节密钥。
- **通知类调用**均为 `await Promise.allSettled`（如 `appointments/route.ts:156-165`），无 fire-and-forget 悬挂 promise；模块级缓存（`media-storage/registry.ts`、`wechat-access-token.ts`、`postgresql.ts`）均有 TTL 或单例，无无界增长。
- **leads 写路径**：`api/leads/[id]/route.ts` PUT 为字段级更新（非整体覆盖），`converted` 状态只能走专用签约接口（302-307 行），提成快照在 `snapshotForConvertedLead`（`lead-commission-repository.ts:292-345`）有 FOR UPDATE + 冲突检测防重复生成。
